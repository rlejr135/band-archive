# 대용량 영상 업로드 데이터 절약 계획

상태: **계획 단계 — 구현·배포·production 검증 전**

## 목표와 비목표

목표는 200 MiB를 넘는 영상을 모바일 사용자가 업로드할 때 **실제 이동통신 데이터 전송량을 줄이는 것**이다. 사용자가 Wi-Fi가 아닌 환경임을 인지하고 선택할 수 있게 하며, 지원 기기에서는 업로드 전에 더 작은 파일을 만드는 선택지를 검증한다.

다음은 이 계획의 비목표다.

- 업로드가 끝난 뒤 서버에서 720p를 만들었다는 이유만으로 최초 업로드 데이터가 줄었다고 주장하지 않는다.
- 기존 원본을 자동 삭제하거나, 사용자의 명시적 선택 없이 화질을 낮추지 않는다.
- 현재 원본 video + M4A 처리 흐름을 이번 계획만으로 720p 저장 구조로 바꾸지 않는다.

서버 후처리 720p는 이후의 재생 트래픽과 R2 저장량을 줄일 수 있지만, 원본을 먼저 전송한 경우 최초 업로드 데이터는 줄이지 못한다. 업로드 데이터 절감의 핵심은 전송 전에 파일을 줄이는 것이다.

## 현재 구조와의 관계

현재 video는 R2에 직접 업로드한다. 100 MiB 이상은 multipart(16 MiB part, 동시성 3)로 보내며, 서버는 완료 후 원본과 추출 M4A를 관리한다. 이 계획은 multipart 계약, M4A queue, 1 GiB video 상한을 즉시 변경하지 않는다.

사전 압축이 선택된 경우에는 압축 산출물이 기존 multipart/single upload 경로로 들어간다. 서버는 해당 파일을 원본 video로 취급하고 M4A를 추출한다. 사전 압축을 선택하지 못하거나 실패하면 현재 원본 업로드를 명확한 확인 뒤 fallback으로 제공한다.

## 접근 방식 비교

| 방식 | 최초 업로드 데이터 | 재생/R2 효과 | 주요 한계 |
| --- | --- | --- | --- |
| 서버 후처리 720p | 줄지 않음 | 720p 제공·원본 삭제 정책에 따라 감소 가능 | 업로드 전송량 문제를 해결하지 못함 |
| 브라우저 사전 압축 | 지원 기기에서 줄일 수 있음 | 작은 업로드 원본에 따라 함께 감소 가능 | 모바일 메모리·발열·호환성·중단 위험 |
| 네이티브 앱/공유 확장 압축 | 가장 예측 가능한 절감 가능성 | 작은 파일 전송으로 함께 감소 | 앱 개발·배포·권한·유지보수 비용 |

브라우저 사전 압축은 WebCodecs, MediaRecorder 또는 브라우저가 허용하는 트랜스코딩 구현을 전제로 하며, 모든 형식/기기에서 동등한 결과를 보장하지 않는다. 네이티브 압축은 장기적으로 더 강한 선택지일 수 있지만 웹 기능의 단순한 확장이 아니다.

## 모바일 위험

### iPhone / iOS 브라우저

대형 video의 decode·encode는 메모리 압박, 발열, Safari의 codec/API 지원 차이, 백그라운드 전환·화면 잠금 시 작업 중단 위험이 있다. photo library에서 선택한 파일의 codec과 브라우저가 다시 인코딩 가능한 codec도 다를 수 있다.

### Android 브라우저

기기 성능·RAM·codec 구현·Chrome/WebView 버전 차이가 크다. 저사양 기기는 페이지 종료나 열 제한이 더 빠를 수 있으며, 제조사 절전 정책도 장시간 인코딩에 영향을 줄 수 있다.

### 웹 공통

압축 중에는 원본과 출력 버퍼가 함께 존재할 수 있어 파일 크기보다 큰 메모리를 사용한다. CPU 사용·배터리 소모·발열로 UX가 나빠질 수 있고, 사용자가 앱을 전환하거나 네트워크가 바뀌면 재개가 어렵다. 따라서 지원하지 않는 환경에서 강제하지 않고, 진행률·취소·실패 설명과 원본 업로드 fallback이 필요하다.

## 권장 단계

1. **전송량과 네트워크 안내**: 200 MiB 초과 video 선택 시 예상 전송량, Wi-Fi 권장, 현재 네트워크 정보를 가능한 범위에서 안내한다. 압축 기능을 구현한 것처럼 표시하지 않는다.
2. **선택형 사전 압축 PoC**: 대표 iPhone/Android/desktop에서 feature detection을 수행한다. 지원되는 환경에만 “데이터 절약용 압축”을 opt-in으로 제공하고, 원본 업로드와 취소 fallback을 유지한다.
3. **품질·안정성 기준 확정**: 실제 업로드 바이트, 완료율, 인코딩 시간, 온도/배터리 불만, 재생 가능성을 측정한다. 기준을 통과하지 못하면 브라우저 압축을 기본값으로 승격하지 않는다.
4. **필요 시 서버 720p 재생 최적화**: 업로드 전송량 절감과 별개로, 재생 데이터와 R2 저장 최적화가 필요할 때만 서버 720p 산출물 전략을 별도 결정·구현한다.

## 미결정 사항

- 200 MiB가 안내만 표시할 기준인지, 사전 압축 제안 기준인지, multipart 기준(현재 100 MiB)과 어떤 관계인지
- 목표 해상도, FPS, video/audio codec, 비트레이트와 품질 허용 한계
- 사전 압축 파일을 유일한 업로드 원본으로 둘지, 원본도 보관할지, 보관 기간·사용자 동의·삭제 정책
- 서버 720p를 도입할 경우 원본·720p·M4A의 저장 수명과 재생 선택 정책
- Wi-Fi/셀룰러 감지의 브라우저별 정확도와 개인정보·권한 안내
- 실패/취소된 사전 압축 산출물 및 multipart session의 보관·정리 기준

## 성공 지표

- 200 MiB 초과 대상에서 사전 압축 선택 시 실제 전송 바이트 감소율
- 선택형 압축의 완료율, 실패/취소율, fallback 원본 업로드 성공률
- 기기별 처리 시간, 페이지 종료·백그라운드 중단 비율, 사용자 불만
- 압축 후 업로드된 video의 서버 M4A 추출 성공률과 재생 호환성
- R2 고아 객체·미완료 multipart session 수 및 정리 성공률

## 롤백과 정리

기능은 feature flag 또는 UI 노출 제어로 즉시 비활성화할 수 있어야 한다. 롤백 시 이미 완성된 원본/M4A는 삭제하지 않는다. 취소·실패한 multipart는 기존 abort API를 호출하고, R2의 abandoned multipart lifecycle/정리 정책은 현재 Cloudflare 계정에서 별도로 확인한다. DB에 완료되지 않은 media 레코드나 R2 고아 객체가 생기지 않는지 배포 후 표본 점검한다.

| --- | --- | --- |
| iPhone Safari | 200 MiB 초과 HEVC/H.264, Wi-Fi/셀룰러 | feature detection, 메모리·발열, 백그라운드/잠금, 압축·fallback·재생 |
| Android Chrome | 200 MiB 초과 H.264 및 기기별 codec | 성능 차이, 취소/재시도, multipart ETag/CORS, M4A 완료 |

| 미지원 브라우저 | 압축 API 없음/실패 | 압축 강제 없음, 원본 업로드 안내와 정상 multipart |
| 네트워크 변화 | 전송 중 오프라인·전환·취소 | 오류 설명, abort, 고아 객체·session 정리 |

PoC 결과가 이 표의 안정성·데이터 절감 기준을 만족한 뒤에만 제품 정책과 실제 구현 범위를 확정한다.
