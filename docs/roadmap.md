# 개선 로드맵

이 문서는 현재 코드의 위험을 줄인 뒤 백엔드 이전 여부를 판단하기 위한 권장 순서다. 일정과 호스팅 선택이 확정된 계획은 아니며, 각 단계의 완료 조건을 충족한 뒤 다음 단계로 진행한다.

## 0. 즉시 조치: 비밀과 접근 통제

- Git에서 `.env`, `k3s/secrets.yaml`과 실제 자격증명의 추적·이력을 점검한다.
- 노출 가능성이 있는 R2, NAVER Search, Flask 비밀값을 회전한다.
- 저장소에는 값 없는 예시 파일만 두고 운영 비밀은 Fly.io/Cloudflare의 secret 저장소에서 관리한다.
- 변경·삭제 API를 목록화하고 서버 측 인증·역할 기반 권한을 설계한다.

완료 조건:

- 실제 비밀이 현재 Git tree와 새 배포 이미지에 없다.
- 모든 변경 API에 명시적인 인증·인가 정책이 있다.

## 1. 기본 안정성

- presigned URL 발급 전에 사용자 권한, 허용 콘텐츠, 최대 크기와 사용량 한도를 검증한다.
- 프론트엔드에 공통 API client, timeout, 요청 취소와 일관된 오류 UI를 도입한다.
- 곡 삭제, 합주 미디어와 영상 파생 객체의 정합성을 수정한다.
- 전역 오류 처리, health endpoint, 구조화 로그와 요청 식별자를 추가한다.
- 기존 테스트를 R2 mock 또는 격리된 테스트 버킷 기준으로 고치고 누락된 도메인 테스트를 추가한다.

완료 조건:

- 인증 없는 변경, 과도한 업로드, 테스트의 실제 운영 R2 접근이 차단된다.
- 핵심 CRUD·업로드·삭제·지도 검색 경로가 CI에서 재현 가능하다.

## 2. 미디어 작업 분리

- API 프로세스 내부 스레드를 내구성 있는 작업 큐로 교체한다.
- FFmpeg를 별도 worker에서 실행하고 동시성, timeout, 재시도와 실패 큐를 관리한다.
- 업로드/트랜스코딩 상태 조회 또는 알림을 제공한다.
- 고아 R2 객체와 깨진 DB 참조를 찾는 정합성 점검 작업을 만든다.

완료 조건:

- API 재시작이나 Fly 자동 suspend 이후에도 작업을 복구할 수 있다.
- API 지연과 트랜스코딩 처리량을 별도 지표로 확인할 수 있다.

## 3. 데이터 계층 정비

- 시작 시 `create_all()`과 수동 SQL에 의존하지 않고 명시적인 migration revision을 운영한다.
- SQLite 백업, 복원과 데이터 무결성 점검 절차를 자동화한다.
- 다중 인스턴스 또는 플랫폼 이전이 필요하면 관리형 PostgreSQL 등 외부 DB로의 전환을 평가한다.

완료 조건:

- 배포 전후 스키마 변경과 롤백 절차가 재현 가능하다.
- 정해진 복구 목표에 맞춰 백업에서 실제 복원이 검증된다.

## 4. 배포 파이프라인 정리

- Cloudflare 프론트엔드 배포를 저장소의 단일 현행 워크플로로 문서화한다.
- 현재 운영과 다른 GitHub Pages 워크플로를 제거하거나 명확히 비활성화한다.
- Fly 배포 전 lint, frontend build, backend tests와 이미지 검사를 수행한다.
- 릴리스마다 Cloudflare 배포 ID와 Fly release/image 식별자를 남긴다.
- k3s는 실제 도입 결정을 내리기 전까지 초안으로 유지하고 운영 secret을 넣지 않는다.

완료 조건:

- 동일 커밋을 재빌드·재배포할 수 있고 FE와 BE를 각각 직전 정상 릴리스로 되돌릴 수 있다.

## 5. 백엔드 호스팅 재평가

안정화 이후 Fly.io 유지, Cloudflare 계열, 관리형 컨테이너/PaaS를 동일한 시나리오로 비교한다.

| 평가 영역 | 측정 항목 |
| --- | --- |
| 사용자 성능 | 한국 기준 API p50/p95 지연, cold start |
| 미디어 처리 | 작업 대기시간, 동시 처리량, CPU·메모리 제한 |
| 데이터 | 외부 DB 연결, 백업·복원, 다중 인스턴스 |
| R2 연계 | 네트워크 지연, egress, 자격증명 관리 |
| 운영성 | 로그, 메트릭, 알림, 롤백, 배포 자동화 |
| 비용 | 평상시·업로드 집중 시 월 비용과 예산 알림 |

Cloudflare 기반 후보가 일반 API에는 적합하더라도 FFmpeg 장시간 처리는 별도 실행 환경이 필요할 수 있다. 따라서 API와 media worker를 같은 플랫폼으로 반드시 옮길 필요는 없다.

완료 조건:

- 실제 부하 테스트와 장애 복구 실험 결과로 플랫폼을 선택한다.
- 이전 계획에 DB, 큐/worker, 환경변수, CORS, 도메인 전환과 롤백이 포함된다.
