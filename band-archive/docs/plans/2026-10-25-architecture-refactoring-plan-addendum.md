# 아키텍처 리팩터링 계획 보완서

작성일: 2026-10-25
대상: [아키텍처 리뷰 대응 리팩터링 계획](2026-10-25-architecture-refactoring-plan.md)

현행 대조(2026-11-04): 원래 1~9절의 설계·검증 기준을 보존하고 실제 구현·선택 보류를 10절에 연결했다. 제품 **`d5cae87`**, 전체 BE **1,738 passed·978 warnings·0 failed·0 skipped**, 일반 push와 **Fly v91 배포 확인 완료**다. 실행 증거·한계는 [단일 최종 보고서](../reports/2026-11-04-architecture-refactoring-final.md)를 따른다.

과거 리뷰·Wave 보고서는 로컬 보조 기록이므로 새 clone에 없을 수 있다. 이 보완서의 기준과 원계획·루트 용어집/지도·실제 코드가 현재 판단의 입력이며, 과거 보고서가 반드시 존재한다고 가정하지 않는다. 이번 최종 검증·배포 증거는 단일 최종 보고서에 기록한다.

## 1. 목적과 적용 범위

원계획의 방향과 저위험 추출 순서는 유지한다. 이 문서는 후속 작업에 필요한 **설계 결정과 검증 기준만 추가**한다. 원계획을 대체하거나 이미 완료한 작업을 다시 수행하도록 요구하지 않는다.

근거는 원계획 본문뿐이다. 실제 코드·테스트·배포 상태와 연결된 결과 보고서는 이번 보완서 작성에서 확인하지 않았다. 원계획에 적힌 BE-1~4 완료, FE 일부 완료, 공개 범위·재생 규칙과 트랜잭션 정리 미착수는 검증한 사실이 아닌 계획서의 진행 기록으로 취급한다.

아래 모듈 책임과 규칙은 후속 설계 기준이다. 특정 파일·함수의 현재 구현이나 검증 완료를 뜻하지 않는다. 실제 이동 대상과 기존 동작은 각 작업을 구현하기 전에 코드로 대조한다. 문서 작성만으로 구현·운영 변경을 시작하지 않는다.

| 우선순위 | 보완 항목 | 원계획에 적용할 위치 |
|---|---|---|
| P1 | BE·FE 각각의 모듈 책임, 공개 함수, 의존 규칙 | 2~5단계의 담당 경계 설계 |
| P1 | 유스케이스별 트랜잭션 소유권과 실패 의미 | 4단계 착수 전 |
| P2 | CSS 순서와 실제 렌더링을 포함한 시각 검증 | 남은 FE 추출 및 검증·배포 게이트 |
| P2 | 필수 테스트의 수집·실행 증거 | 3~4단계 및 영향받는 릴리스 묶음 |
| P2 | 단계 번호 대신 실제 선행 조건으로 착수 판단 | 실행 순서와 병렬화 |

새 아키텍처 문서 체계를 여러 개 만들 필요는 없다. 다음 절의 표를 이 문서나 담당 작업 기록에 채우면 된다. 처음부터 전체 도메인의 설계를 확정하기보다 다음 변경이 건드릴 경계를 먼저 정한다.

## 2. 단계별 착수 조건 보완

단계 번호는 권장 순서다. **전체 FE 화면 분리 완료를 모든 BE 작업의 공통 선행 조건으로 두지 않는다.** 각 작업의 관련 의존·설계·검증 준비가 충족됐는지 판단한다.

| 후속 작업 | 착수 전에 필요한 사항 | 전체 완료를 기다릴 필요가 없는 작업 |
|---|---|---|
| 남은 FE 화면 추출 | 해당 기능의 상태 소유자·소비자·스타일 로딩·보존 계약 확인 | 관련 없는 BE 고위험 작업 |
| 3단계 공개 범위·재생 규칙 | BE 책임표, URL 발급 경로 목록, 인가·signing 계약표, 필수 테스트 실행 경로 | 관련 없는 FE 화면 추출 |
| 4단계 일반 DB 트랜잭션 | 담당 유스케이스의 트랜잭션 책임표, 기존 실패·재요청 의미, 관련 동시성 검증 | 관련 없는 FE 추출과 업로드 재설계 |
| 4단계 업로드 정리 | 업로드 단계별 commit·잠금·재인가·복구 설계와 필수 경쟁 테스트 | 일반 DB 업무 전체의 전환 |
| 5단계 v2 응답 serializer 전환 | 해당 응답의 기존 계약과 관련 접근·재생 경계 확정 | 전체 기능의 폴더 재배치 |
| 6단계 조회 hook 공통화 | 추출한 기능 간 실제 반복과 서로 다른 병합·취소 정책 확인 | 공통화와 무관한 화면 추출 |
| 7단계 schema 모듈 검토 | 기존 작업 안정화, 실제 탐색 비용, migration 재현 검증 준비 | 원계획대로 선택 단계 유지 |

서로 다른 파일을 바꾼다는 이유만으로 동시에 전환하지 않는다. 공통 함수, 응답 계약, 잠금 순서, 상태 수명에 영향을 주는 작업은 선행 변경을 통합·검증한 뒤 진행한다. 필요한 설계 기록과 검토는 기존 총괄 리뷰 절차에 포함하며 새로운 사용자 승인 절차를 추가하지 않는다.

## 3. BE Target Architecture에 추가할 결정

### 3.1 책임과 의존 방향

| 역할 | 소유하는 책임 | 경계 |
|---|---|---|
| HTTP route | 요청 파싱, 인증 진입, 서비스 호출, 기존 HTTP 응답·헤더 구성 | 다른 기능의 route를 공통 라이브러리로 사용하지 않음 |
| 유스케이스 | 하나의 업무 처리 조정, 인가 재확인, 변경·audit의 원자성, 일반 DB 업무의 commit/rollback | 하위 helper가 호출자의 업무를 중간 commit하지 않음 |
| 기능별 query | 밴드 범위·공개 범위·관계·차단·삭제 대기를 반영한 SQL과 필요한 그래프 준비 | SQLAlchemy 직접 사용 가능. HTTP 응답·commit을 소유하지 않음 |
| 업무 규칙 | 준비된 입력의 공개 범위·관계 유효성·재생 소스 선택 등 판단 | 순수 규칙은 HTTP·DB·R2에 접근하지 않음. lazy load가 가능한 ORM 접근과 구분 |
| 재생 접근 서비스 | 요청 scope와 대상의 접근 자격 확인, 필요한 상태 조회, TTL·소스 결정 후 signing 조정 | 권한이 확인되지 않은 object key를 외부 입력만으로 서명하지 않음 |
| serializer | 허용된 데이터를 기존 envelope·JSON 필드로 변환 | 상위 유스케이스나 route를 호출하지 않음. DB 변경·commit을 하지 않음 |
| 인프라 adapter | R2·FFmpeg 등 특정 구현체의 작업 수행 | 지원되는 호출 경로의 보호가 확보되기 전 기존 guard를 제거하지 않음 |

읽기는 route → query/접근 서비스 → serializer로 처리할 수 있다. 단순 조회에도 빈 유스케이스 계층을 의무적으로 추가하지 않는다. 기능별로 필요 없는 파일·클래스는 만들지 않는다.

의존 규칙:

1. 앱 조립 코드의 blueprint 등록을 제외하고 제품의 다른 모듈이 `routes.*` 구현에 의존하지 않는 방향으로 정리한다. private 함수 이름만 public으로 바꾸는 것은 해결로 인정하지 않는다.
2. 다른 도메인과 협력할 때는 그 도메인이 공개한 서비스·조회 함수를 사용한다. 협력의 조정 책임은 해당 유스케이스에 둔다.
3. 하위 모듈이 호출자를 다시 import하는 순환을 만들지 않는다. 함수 내부 import로 옮기는 것만으로 의존이 해소됐다고 기록하지 않는다.
4. 공유 범위는 명시한다. 밴드 SQL 조건 같은 공통 기반과 곡·갤러리·공지의 기능별 조회를 구분한다.

### 3.2 담당 모듈별로 채울 책임표

| 기록 항목 | 작성 내용 |
|---|---|
| 담당 업무 | 예: 곡 제안 채택, 갤러리 조회, 미디어 재생 접근 |
| 소유 규칙·데이터 변경 | 해당 모듈이 최종 책임지는 업무와 불변 조건 |
| 공개 함수 | 이름, 입력, 반환값, 오류, 잠금·부수효과·commit 여부 |
| 허용 의존 | 사용하는 인가·query·다른 도메인의 공개 함수·인프라 |
| 소비자 | route, worker, 운영 도구, legacy 경로 중 실제 호출자 |
| 공통/집계 판단 | 공통 기반인지 특정 기능인지, 여러 도메인 집계가 필요한 이유 |
| 이동·호환 방식 | 소비자 교체 순서와 임시 shim이 필요할 경우 제거 조건 |

`content_queries.py`처럼 여러 도메인의 코드가 모인 파일은 현재 추출 단계의 경계로 사용할 수 있다. 다만 이를 최종 도메인 분리 완료로 기록하지 않는다. 새 query를 추가할 때 기능별 소유자를 정하고, 대시보드 같은 집계 조회는 여러 도메인을 조합한다는 책임을 명시한다. 파일 크기만으로 즉시 재분할하지 않는다.

## 4. FE Target Architecture에 추가할 결정

### 4.1 구성요소와 상태 소유권

| 역할 | 책임·상태 |
|---|---|
| 앱 조립·라우팅 | provider 구성과 실제 route 연결 |
| 밴드 shell | 밴드 해석, 계정·멤버십 경계, 탐색, Outlet |
| 기능 화면 | 해당 화면의 목록·상세·선택·열린 폼과 기능 조정 |
| 폼 | 입력 초안, 검증 표시, 제출 상태. 기존 공개 범위 확인 절차 보존 |
| 조회 hook | 해당 자원의 loading/error/page/request 수명과 명시적 갱신 |
| API adapter | 경로·payload·응답 변환. 최종 권한 판단은 서버 계약을 따름 |
| 공통 UI·작은 helper | 실제 여러 소비자가 사용하는 표현·순수 계산 |
| 업로드 provider/controller | 페이지 이동을 넘어 유지할 작업·취소·재시도·완료 알림 |

인증·정책·밴드 선택의 기존 provider 책임과 수명은 유지한다. 화면 추출을 이유로 전역 상태를 추가하거나 기존 상태를 일괄 전역화하지 않는다.

의존 규칙:

1. shell은 기능 화면을 조립할 수 있지만 기능 화면·공용 편집기는 shell 구현을 역으로 import하지 않는다.
2. 다른 기능이 재사용하는 편집기·helper는 독립 진입점으로 공개한다. 원래 큰 화면 파일에서 다시 helper를 가져오지 않는다.
3. 임시 re-export를 유지하면 실제 소비자와 제거 조건을 기록한다. 새 소비자를 임시 진입점에 추가하지 않는다.
4. BE와 FE의 폴더를 일대일로 맞추지 않는다. FE의 화면 조합과 BE의 업무 원자성은 서로 다른 경계다.

### 4.2 남은 화면 추출별로 채울 상태표

| 기록 항목 | 작성 내용 |
|---|---|
| 화면·폼 경계 | 이동할 책임과 그대로 남길 shell 책임 |
| 상태 소유자 | 서버 데이터, 선택 항목, 입력 초안, 처리 중 상태의 소유자 |
| 상태 폐기 조건 | 계정·밴드·멤버십·선택 대상 변경 시 무엇을 초기화하는지 |
| 요청 유효성 | identity key, generation, abort, 응답 검증과 늦은 응답 차단 방식 |
| 데이터 갱신 | mutation·업로드 완료·URL 만료 후 다시 읽거나 병합할 대상 |
| 공유 소비자 | 관리 화면·일반 화면이 공유하는 부분과 권한·조회 차이 |
| 스타일 의존 | 필요한 CSS 진입점과 기존 선언 순서 |

곡·일정 등 서로 다른 기능을 새 범용 설정 객체로 다시 묶지 않는다. 곡·일정 각각의 화면·폼을 명시하고, 동일한 작은 입력·전송 부분만 공유한다.

## 5. BE–FE 공통 계약표 추가

계약에 영향을 주는 작업에만 해당 행을 작성한다. 전체 API 명세나 타입 생성 체계의 신규 도입은 요구하지 않는다.

| 대상 | 기록할 현재 계약 |
|---|---|
| HTTP | method/path, 인증·optional auth, 상태 코드, 오류 본문, cache·관련 헤더 |
| 응답 | envelope, 필드 이름·타입·null/누락 의미, 페이지네이션 |
| 권한 | capability 필드와 서버 판단, 일반 조회와 관리 조회의 차이 |
| 상태 | 업로드·추출·삭제의 상태 필드, 완료·실패·재시도 의미 |
| 재생 | URL 종류, TTL, 원본·720p·M4A 선택, 차단·삭제 대기 처리 |
| FE 갱신 | 성공 응답의 반영 대상, 재조회·append·replace·dedupe/update 방식 |
| 호환 소비자 | v1/v2, 현재 웹, 남아 있는 native·운영 경로의 실제 사용 여부 |

이 표는 현재 계약을 보존하기 위한 것이다. 같은 개념처럼 보여도 서로 다른 envelope·투표 주체·상태 이름을 자동 통일하지 않는다. 목록 필터·객체 판단·signing 검사는 같은 시나리오 입력과 권한 맥락에서 대조한다. 비회원 일반 조회와 별도 관리 경로의 결과가 같아야 한다고 요구하지 않는다.

## 6. 트랜잭션 책임 명세 추가 — P1

### 6.1 일반 DB 업무의 기본 결정

일반 DB 변경은 **명시적인 유스케이스 함수가 업무 트랜잭션의 commit/rollback을 소유**하는 방향으로 설계한다. route는 요청·응답을 맡고, 하위 helper는 필요한 flush만 수행한다. 이 결정으로 기존 코드를 일괄 변경하지 않고 전환 대상 유스케이스에만 적용한다.

기존 session에서 이미 시작된 transaction, auth 동기화의 commit, 테스트 fixture의 transaction을 실제 코드로 확인한 후 구현 방식을 정한다. 이를 확인하지 않은 `session.begin()` 중첩·강제 rollback·임의 session 교체는 하지 않는다.

### 6.2 첫 대상: 곡 제안 채택

아래 표는 착수 전에 실제 코드와 계약을 확인해 채운다. 미확인 항목을 이미 결정된 사실로 기록하지 않는다.

| 결정 항목 | 반드시 확정할 내용 |
|---|---|
| 진입점·소유자 | 실제 route와 유스케이스 함수, commit/rollback 담당 함수 |
| 호출자 session | 인증·계정 동기화 뒤 session 상태, 기존 transaction과 연결 방식 |
| 재인가·잠금 | 현재 actor·밴드·가입 관계·제안의 검사 시점과 실제 잠금 순서 |
| 원자적 업무 | 곡 생성, 제안 제거, 관련 audit 등 현재 함께 반영돼야 하는 변경 |
| 하위 호출 | helper별 DB 조회·변경·flush·commit 허용 여부 |
| 응답 생성 | 기존 응답 형태와 직렬화·commit의 실행 순서 |
| 실패 | 검증·flush·commit·직렬화 각각의 실패 시 DB 결과와 HTTP 의미 |
| 재요청·경쟁 | 중복 요청, 동시 채택, commit 성공 후 응답 유실 시 현재 동작 |

새 멱등 키나 outbox를 이 작업에 추가하지 않는다. 현재 audit/outbox가 있는 업무에서는 기존 원자성을 보존하되, 곡 제안 채택에 outbox가 있다고 가정하지 않는다.

**응답 실패를 DB 실패와 구분한다.** commit 성공 후 응답 직렬화나 전송이 실패하면 이미 반영된 변경을 rollback한 것으로 취급할 수 없다. 현재 순서와 재요청 동작을 먼저 기록한다. 순서 변경이 외부 동작을 바꾸면 기계적 추출과 별도 변경으로 분리한다.

### 6.3 업로드는 별도 단계표 사용

업로드에는 일반 DB 업무의 단일 commit 규칙을 적용하지 않는다. 원계획의 다중 단계 구조를 유지하고 아래 항목을 단계마다 작성한다.

| 단계 | 추가 기록 |
|---|---|
| claim 저장 | 상태 전이 조건, durable commit 위치, 경쟁 요청 결과 |
| 외부 확인 | HEAD 등 I/O와 timeout 처리, DB 잠금 보유 여부 |
| 재인가·레코드 생성 | 실제 재인가·잠금 범위, 용량 예약, 생성의 원자성 |
| 완료 기록 | commit 위치, 이미 생성된 결과 재조회, 멱등 완료 |
| 실패·복구 | 실패 지점별 DB/R2 상태, 예약 유지·해제 조건, 재시도 담당자 |

기존 잠금을 추측으로 제거하거나 R2 I/O 전체를 긴 DB 트랜잭션으로 감싸지 않는다. 필요한 중간 commit과 복구 기록을 유지한다.

## 7. CSS·시각 검증 보완 — P2

원계획의 CSS rule fragment 정렬 비교는 선언 집합 비교의 보조 자료로 사용한다. **정렬 후 같다는 사실이나 파일 길이가 같다는 사실만으로 렌더링 동일성을 확정하지 않는다.** import·선언 순서가 바뀌면 cascade 결과도 달라질 수 있다.

FE 추출마다 영향받는 화면에서 다음을 확인한다.

1. 기존 CSS가 어떤 import 경로와 순서로 로드됐고 추출 후 어떻게 로드되는지 기록한다.
2. 같은 specificity의 충돌, 전역 selector와 공용 class의 중첩, 누락된 stylesheet를 확인한다.
3. 고정 mock 데이터·같은 viewport에서 전후 화면을 비교한다. PC/모바일과 해당 기능의 빈 목록·오류·폼 열림 등 영향받는 상태를 대상으로 한다.
4. 차이가 있으면 의도된 디자인 변경으로 자동 정당화하지 않고 원인을 분류한다. 구조 이동 묶음에는 재디자인을 섞지 않는다.

전체 제품의 새 시각 회귀 시스템을 도입할 필요는 없다. 변경된 화면의 비교 결과와 확인한 스타일 범위를 남기면 된다. 이번 지적은 이미 배포된 화면에 결함이 있다는 판정이나 자동 롤백 요청이 아니다.

## 8. 필수 검증의 실행 증거 보완 — P2

총 passed 수·0 skipped와 **변경에 필요한 테스트가 실제 수집·실행됐는지**를 구분한다. 기존 통합 테스트를 유지하면서 해당 묶음의 필수 시나리오를 명시한다.

| 작업 | 필수 시나리오의 출발점 |
|---|---|
| 공개 범위·재생 규칙 | 같은 권한 맥락에서 SQL/객체 판단 일치, 부모·자식 범위, 깨진 밴드 관계, 차단·삭제 대기 signer 0회, pruned 원본 signing 0회, 소스·TTL 보존 |
| 일반 DB 트랜잭션 | 중간 실패·commit 실패 시 원자성, audit 동반 반영, 현재 중복 요청·경쟁 결과, commit 이후 응답 실패의 의미 |
| 업로드 | 실제 PG의 관련 잠금·예약 경쟁, timeout·HEAD·재시도·탈퇴 경쟁, 단계별 복구 |
| FE 화면·hook 추출 | 계정·밴드·멤버십·선택 변경, 역순 응답, unmount·abort, 업로드 완료 갱신, 기존 페이지 병합·URL 갱신 |
| schema 모듈 | 지원 revision upgrade, 현재 계약 diff, 실제 PG 제약·보안 계약, 읽기 전용 startup과 fail-closed |

작업마다 다음 형식으로 증거를 남긴다.

| 항목 | 기록 |
|---|---|
| 기준 | 검증한 commit과 변경 범위 |
| 실행 | 실제 명령, 선택 조건·marker·필요 환경, 관련 runtime 버전 |
| 필수 대상 | 시나리오에 대응하는 정확한 테스트 node ID 또는 FE 테스트 이름 |
| 수집·실행 | 필수 대상의 collected/executed 수와 passed/failed/skipped 결과 |
| PG | 사용한 로컬 소유 PG 버전, 실제 실행 여부와 정상 정리 여부 |
| 외부 I/O | R2·signer fake 사용 범위와 실제 호출을 검증한 경계 |
| FE 시각 확인 | 화면·viewport·mock 상태와 비교 결과 |
| 미확인 | 미실행·미확인 항목, 해당 작업 완료 판정에 미치는 영향 |

PG marker가 선언돼 있거나 전체 suite가 통과했다는 이유로 PG 실행 완료를 기록하지 않는다. 해당 변경의 필수 테스트가 누락·skip되면 그 검증은 미완료다. 필요한 PG 실행 환경이 없으면 영향받는 고위험 작업의 완료 판정을 보류한다. 무관한 FE 추출까지 일괄 중단하는 의미는 아니다.

## 9. 완료 판정과 다음 실행 단위

이 절의 다음 실행 목록은 2026-10-25에 정한 권장 순서다. 현재 구현과 보류 판단은 10절 및 원계획 추적표를 따른다.

완료 판정은 두 수준으로 구분한다.

- **추출 묶음 완료:** 담당 소비자 전환, 기존 계약·검증 보존, 해당 경계의 역방향 의존 제거.
- **아키텍처 경계 완료:** 책임·공개 함수·허용 의존·상태 또는 트랜잭션 소유자가 명시되고, 변경 시 관련 없는 도메인을 수정하지 않아도 되는 구조가 확인됨.

다른 도메인과의 정상적인 업무 협력까지 없애거나 수정 파일 수를 임의의 숫자 이하로 제한하지 않는다. 대표 변경 하나를 따라가며 **어느 도메인을 왜 수정해야 하는지**를 설명할 수 있는지 확인한다. 기능 삭제의 영향은 소비자·등록·공유 규칙을 추적해 평가하며 검증을 위해 실제 기능을 삭제하지 않는다.

권장 다음 실행 단위:

1. 남은 FE 추출은 담당 화면의 상태표·스타일 의존을 먼저 기록한 뒤 원계획대로 진행한다.
2. 3단계 전에는 재생 접근 서비스와 기능별 query·규칙·serializer의 책임표, 호출 경로 목록, 공통 계약표, 필수 테스트 목록을 작성한다.
3. 4단계 전에는 첫 유스케이스인 곡 제안 채택의 트랜잭션 책임표를 채운다. 미확정 순서·실패 의미를 정리한 뒤 추출한다.
4. 각 구현 묶음의 결과에는 원계획의 검증·배포 기록과 함께 이 보완서의 필수 검증 실행 증거를 남긴다.

이 보완서 작성 시점에는 코드·원계획·운영환경을 변경하지 않았고 테스트를 실행하지 않았다. 실제 구현·배포는 원계획과 기존 프로젝트 작업 지침을 따른다.
