# 밴드 공유 가능 시간 캘린더 계획 (초안)

작성일: 2026-10-17. 사용자 요청은 계획 수립이며 구현·운영 DB 변경은 아직 승인되지 않았다.

## 목표와 현재 구조

합주 일정을 정하기 위해 같은 밴드의 활성 멤버가 가능 시간을 등록하고, 겹치는 시간과 미응답자를 확인한다. 개인 일정의 제목·장소·사유를 공유하는 범용 개인 캘린더는 만들지 않는다.

현재 `BandActivityDashboard`는 월별 확정 합주를 `react-calendar`로 표시한다. 실제 밴드 합주 화면은 `BandWorkspace`와 v2 API를 사용한다. 구형 `RehearsalCalendar`/v1 API를 새 기능에 다시 연결하지 않는다. `Rehearsal`은 날짜·선택적 날짜 범위·문자열 `time`을 보관하지만 구조화된 시작/종료 시각이나 가용 시간 모델은 없다.

## 권장 MVP 사용자 흐름

1. 밴드 공간의 **합주** 안에 `확정 일정 / 일정 조율`을 둔다. 대시보드에는 확정 일정과 일정 조율 바로가기만 두어 관리 화면처럼 바꾸지 않는다.
2. 각 멤버는 날짜를 선택하고 30분 단위로 가능·불가·미정 시간대를 입력한다. 날짜별 `입력 완료`를 명시하며, 미입력 구간은 언제나 미정이다. 여러 구간과 하루 전체 입력을 지원한다.
3. 월 보기에는 날짜별 요약, 주 보기에는 시간대별 가능 인원과 멤버별 상태를 표시한다. 모바일은 날짜 → 시간 구간 선택 방식이며 드래그만으로 조작하도록 만들지 않는다. 텍스트·아이콘을 함께 써 색상에만 의존하지 않는다.
4. 조율할 멤버와 필요한 연속 합주 시간(기본 2시간)을 선택한다. 전원 가능 후보를 먼저, 그다음 가능 인원 많은 후보를 표시한다. 가능/불가/미정 인원을 각각 표시하고 조건부 결과를 전원 가능으로 표현하지 않는다. 같은 조건이면 빠른 날짜·시각 순이다.
5. owner/admin은 후보에서 `이 시간으로 합주 만들기`를 눌러 기존 합주 폼으로 이동한다. 날짜·시작·종료를 채우고 제목·장소·곡을 확인하여 저장한다. 자동 예약·자동 확정은 하지 않는다. 저장 직전에 최신 가용 시간을 재검사하고 변경이 있으면 경고·재확인을 요구한다.
6. 확정 합주는 기존 대시보드·합주 목록에 한 번만 나타난다. 가용 시간은 조율 참고 자료이며 합주 참석 확약이나 개인 일정 예약으로 취급하지 않는다.

## 공개·권한·데이터 경계

- 밴드가 PUBLIC이어도 가용 시간과 멤버별 집계는 활성 밴드 멤버에게만 제공한다. 방문자·가입 대기·탈퇴·다른 밴드는 접근할 수 없다.
- 계정과 연결된 실제 `BandMembership`으로 입력한다. 로그인 계정이 없는 기존 `Member` 프로필은 응답자로 만들거나 다른 사람이 대신 입력하지 않는다. 조율 대상 멤버는 서버에서 같은 밴드의 활성 가입 여부를 검증한다.
- 각자 본인의 가용 시간만 입력·수정한다. 관리자가 다른 멤버의 개인 시간표를 변경하지 않는다. 역할별 `can_*`는 서버가 결정한다.
- 같은 사용자의 다른 밴드 시간표를 자동 합치거나 공유하지 않는다. 입력 자료는 밴드별로 독립적이다.
- 밴드 탈퇴 시 해당 멤버는 조율 대상·집계에서 즉시 제외되고 시간표 조회도 차단된다. 기존 확정 합주·곡·업로드 등은 기존 보존 정책을 유지한다. 가용 시간 자체의 보관·파기 기한은 구현 전 별도 결정하며 무기한 보관을 기본값으로 약속하지 않는다.
- 기존 ‘콘텐츠 삭제는 owner/superadmin만’ 정책은 확정 합주 등에서 유지한다. 본인 가용 시간 초기화·철회는 개인정보성 설정 변경으로 허용하는 예외를 제안하지만, 사용자 확인 전 확정하지 않는다.

## 데이터·API 설계 방향

- `BandAvailabilityDay`: band_id, membership_id, local_date, submitted_at, revision. 밴드·멤버·날짜 유일 제약으로 하루 한 제출 단위를 유지한다.
- `BandAvailabilityInterval`: 부모 day_id, 시작·종료 시각, 상태(AVAILABLE/UNAVAILABLE). 명시 구간 외에는 UNKNOWN으로 계산한다. 같은 날 구간의 중복·역전·30분 단위·경계와 부모/멤버 band 정합성을 검증한다.
- 밴드 일정 기준 시간대는 MVP에서 `Asia/Seoul` 고정이다. 날짜 입력은 KST로 해석하고, 시점은 UTC로 저장한다. 끝 시각은 미포함으로 계산하며 자정 넘는 구간은 날짜별로 분할한다. 기기 현지 시간대로 날짜가 바뀌지 않게 한다.
- `Rehearsal`에는 새 일정용 nullable 구조화 시작·종료 시점을 추가하는 additive migration을 검토한다. 기존 문자열 time을 임의 파싱하거나 기존 합주를 변환하지 않는다. 신규 일정만 구조화된 값을 기록하고 기존 응답 필드는 호환 제공한다.
- 초안 경로: GET `/api/v2/bands/{bandId}/availability?from=...&to=...`, PUT `/availability/me/{date}`, POST `/availability/candidates`.
- 하루 단위 교체 저장 + 기대 revision으로 경합 시 409를 반환해 다른 기기의 수정을 덮어쓰지 않는다. 재전송은 멱등 처리한다. 철회 API는 위 정책 예외 확인 후 결정한다.
- 월 화면에 필요한 최대 42일 범위만 조회한다. 기간·조율 대상 수·본문·후보 수를 제한하고, 밴드·날짜·멤버 인덱스로 처리한다. 하루·시간 슬롯별 개별 HTTP 요청, 전체 회원의 전 기간 스캔, N+1 조회를 피한다.
- 기존 인증 클라이언트·band-scope·역할 검증·오류 형식·밴드 전환 시 요청 취소 규칙을 재사용한다. 최초 버전에는 WebSocket, 별도 큐, 상시 백그라운드 계산을 추가하지 않는다.

## 단계·커밋·검증

1. 사용자 선택 확정: 개인 공유 일정 vs 가능 시간, 입력 세밀함, 초기화 예외, 보관 기준을 확정하고 UX/API 계약을 기록한다.
2. BE 모델·migration·가용 시간 검증 및 권한 테스트. 기존 테이블 파괴적 변경은 하지 않는다.
3. BE 날짜별 저장·집계·후보 계산, revision 경합·기간 제한 테스트.
4. FE 월/주 조율 UI·모바일 입력·밴드 변경 격리. 기존 테마 토큰을 사용한다.
5. 기존 합주 생성 폼 연결·구조화된 시간 호환·중복 저장 방지.
6. 전체 BE/FE 테스트·빌드·시각 검증. 각각 단위 커밋하며 구현은 서브에이전트, 총괄은 리뷰·검증을 담당한다.
7. 운영 DB 변경은 사용자 별도 승인 후 백업·복원 검증을 거쳐 적용한다. 이후 상시 승인 범위의 BE/FE 배포와 실제 API·권한·화면 확인을 수행한다.

필수 테스트: 두 밴드 교차 접근, 타인 시간표 변경 차단, 탈퇴 후 접근 차단·집계 제외, 미응답 0명 가능 오인 방지, 전원 미응답, 연속 2시간 부족, 부분 겹침, 자정·월 경계·윤일·KST, 동시 저장 409, 가용 시간 변경 후 확정 경고, 중복 합주 생성 방지, 기존 날짜 범위 합주 회귀, 모바일 키보드/터치 및 밴드 전환 중 지연 응답 차단.

## 이번 MVP에서 제외

- Google/Apple 캘린더 OAuth·양방향 동기화·다른 밴드의 일정 자동 충돌 확인: 외부 권한과 별도 동기화 정책이 필요하므로 나중에 검토한다.
- 개인 일정 제목·장소·사유, 반복 일정, 정교한 참석 투표·응답 마감, 푸시·메일 알림: 우선 수동 가용 시간 입력과 후보 확인의 사용성을 검증한다.
- R2 작업·미디어 재변환·스케일 변경, 보류한 정책 공표·필수 동의 활성화: 이 계획에 포함하지 않는다. 다만 가용 시간도 이용자 생활 패턴에 관한 자료이므로 실제 외부 공개 전에 개인정보 안내 범위를 다시 검토한다.

## 사용자 확인 대기

1. 권장 방식인 ‘개인 일정 내용 없이 가능/불가/미정 시간만 공유’가 맞는지, 아니면 실제 개인 일정도 함께 표시하려는지.
2. 30분 단위 시간 입력과 연속 합주 시간 검색이 필요한지, 날짜별 가능/불가만 표시하는 더 단순한 버전을 원하는지.
3. 본인 가용 시간은 본인이 초기화·철회할 수 있도록 기존 콘텐츠 삭제 정책의 예외로 둘지.

초안의 범위·기본값은 아직 구현 결정이 아니며 위 확인 결과로 조정한다.
