# 밴드 공유 가능 시간 캘린더 계획 (초안)

작성일: 2026-10-17. 사용자가 구현·테스트·운영 배포를 승인했다. 신규 운영 DB 테이블도 로컬 테스트와 운영 백업·복원 검증 후 추가하도록 별도 승인했다. 배포 검증 중 실제 멤버 일정 초기화는 실행하지 않는다.

## 목표와 현재 구조

합주 일정을 정하기 위해 같은 밴드의 활성 멤버가 가능 시간을 등록하고, 겹치는 시간과 미응답자를 확인한다. 2026-10-17 사용자 선택에 따라 날짜별 오전·오후·저녁 세 시간대로 단순화한다. 개인 일정은 선택 입력이며, 가능 시간 입력을 위해 일정 내용이나 사유를 작성할 필요는 없다. **외부 캘린더 연동은 설계·구현 대상에서 완전히 제외한다.** 합주 후 owner가 조율 자료를 초기화하고 각자 새로 등록하는 반복 흐름을 지원한다.

현재 `BandActivityDashboard`는 월별 확정 합주를 `react-calendar`로 표시한다. 실제 밴드 합주 화면은 `BandWorkspace`와 v2 API를 사용한다. 구형 `RehearsalCalendar`/v1 API를 새 기능에 다시 연결하지 않는다. `Rehearsal`은 날짜·선택적 날짜 범위·문자열 `time`을 보관하지만 구조화된 시작/종료 시각이나 가용 시간 모델은 없다.

## 권장 MVP 사용자 흐름

1. 밴드 공간의 **합주** 안에 `확정 일정 / 일정 조율`을 둔다. 대시보드에는 확정 일정과 일정 조율 바로가기만 두어 관리 화면처럼 바꾸지 않는다.
2. 각 멤버는 날짜를 선택하고 오전·오후·저녁 각각에 `가능 / 불가 / 미정`을 입력한다. 예를 들어 오전 불가·오후 가능·저녁 가능을 한 번에 저장한다. 기본값과 초기화 후 상태는 미정이며, 응답하지 않은 것을 불가 또는 가능으로 취급하지 않는다. 하루 전체 일괄 설정과 시간대별 초기화를 지원한다.
3. 월 보기의 각 날짜에는 세 시간대별 가능 인원을 요약하고, 날짜를 누르면 멤버별 세 칸의 표를 표시한다. 모바일은 날짜 선택 → 오전·오후·저녁 버튼 방식이다. 텍스트·아이콘을 함께 써 색상에만 의존하지 않는다. 선택 개인 일정은 별도 접기 영역에서 입력한다.
   - 일괄 입력용으로 날짜가 행, 오전·오후·저녁이 열인 표를 제공한다. PC에서는 여러 칸을 드래그해 선택하고 한 번에 `가능`으로 설정한다. 예: 여러 날짜의 저녁 열 또는 주말의 세 시간대 전체를 선택한다. `불가 / 미정`도 같은 일괄 설정 도구로 지원한다.
   - 드래그는 직사각형 날짜×시간대 선택으로 정의하고 선택 영역을 미리 표시한다. 선택만으로 서버에 저장하지 않으며 `선택한 N칸을 가능으로 저장`에서 한 번에 반영한다. 취소하면 기존 상태를 유지한다.
   - 모바일에서도 터치 범위 선택을 제공하되 일반 세로 스크롤과 충돌하지 않게 선택 모드를 분리한다. 드래그가 어려운 경우 날짜 범위·시간대 체크 및 개별 버튼으로 같은 작업을 할 수 있게 한다. 키보드 조작도 제공한다.
4. 조율할 멤버를 선택하면 날짜×시간대별 전원 가능 후보를 먼저, 그다음 가능 인원 많은 후보를 표시한다. 가능/불가/미정 인원을 각각 표시하고 조건부 결과를 전원 가능으로 표현하지 않는다. 같은 조건이면 빠른 날짜·오전·오후·저녁 순이다. 세 시간대는 대략적인 조율 단위이며, 특정 시작 시각이나 연속 2시간 가능을 보장하지 않는다.
5. owner/admin은 후보에서 `이 시간대로 합주 만들기`를 눌러 기존 합주 폼으로 이동한다. 날짜와 선택 시간대를 보여주고 정확한 시각·제목·장소·곡은 직접 확인하여 저장한다. 임의의 시작·종료 시각을 채우거나 자동 예약·자동 확정하지 않는다. 저장 직전에 최신 가용 시간을 재검사하고 변경이 있으면 경고·재확인을 요구한다.
6. 확정 합주는 기존 대시보드·합주 목록에 한 번만 나타난다. 가용 시간은 조율 참고 자료이며 합주 참석 확약이나 개인 일정 예약으로 취급하지 않는다.
7. 합주 후 owner가 `모두의 조율 일정 초기화`를 실행한다. 현재 밴드의 등록된 가능/불가 상태와 선택 개인 일정 메모를 비우고 전원을 미정·미등록으로 돌려 새 조율 회차를 시작한다. 초기화 전 대상 밴드·범위·영향받는 멤버/입력 건수와 메모 삭제 여부를 명시하고 확인을 받는다. 자동 초기화하지 않으며 확정 합주·곡·영상·댓글·다른 밴드는 변경하지 않는다.
8. 멤버에게 `owner가 일정을 초기화했습니다. 가능한 일정을 다시 등록해 주세요.`와 미등록 상태를 보여준다. 전체 초기화는 owner 전용이고 admin·일반 멤버에게는 노출·허용하지 않는다. 이전 화면의 저장은 거부하여 초기화한 일정이 되살아나지 않도록 한다. 이메일·푸시 발송은 추가하지 않는다.

## 공개·권한·데이터 경계

- 밴드가 PUBLIC이어도 가용 시간과 멤버별 집계는 활성 밴드 멤버에게만 제공한다. 방문자·가입 대기·탈퇴·다른 밴드는 접근할 수 없다.
- 계정과 연결된 실제 `BandMembership`으로 입력한다. 로그인 계정이 없는 기존 `Member` 프로필은 응답자로 만들거나 다른 사람이 대신 입력하지 않는다. 조율 대상 멤버는 서버에서 같은 밴드의 활성 가입 여부를 검증한다.
- 각자 본인의 가용 시간만 입력·수정·삭제·초기화한다. **owner에게는 밴드 전체 조율 일정 초기화 권한을 추가한다.** 이는 타인의 상태를 임의로 가능/불가로 대신 입력하는 권한은 아니다. admin에게는 전체 초기화 권한을 주지 않는다. 역할별 `can_*`는 서버가 결정한다.
- 개인 일정은 선택 입력이다. 구현 기본값은 비공개이며, 본인이 명시적으로 선택한 일정만 같은 밴드에 공개한다. 비공개 본문은 다른 멤버·owner/admin·superadmin용 조율 응답에 포함하지 않는다. 일정 내용으로 가능/불가를 자동 추정하지 않는다. 본인 메모는 본인이 수정·삭제할 수 있다.
- owner의 전체 초기화는 현재 밴드의 선택 메모도 대상으로 하되, 비공개 메모를 읽는 권한을 추가하지 않는다. 초기화 안내에서 해당 메모가 보존되는 개인 일기장이 아니라 회차별 조율 자료라는 점을 분명히 한다. 다른 밴드의 개인 메모나 계정 정보는 초기화하지 않는다.
- 같은 사용자의 다른 밴드 시간표를 자동 합치거나 공유하지 않는다. 입력 자료는 밴드별로 독립적이다.
- 밴드 탈퇴 시 해당 멤버는 조율 대상·집계에서 즉시 제외되고 시간표 조회도 차단된다. 기존 확정 합주·곡·업로드 등은 기존 보존 정책을 유지한다. 가용 시간 자체의 보관·파기 기한은 구현 전 별도 결정하며 무기한 보관을 기본값으로 약속하지 않는다.
- 기존 ‘콘텐츠 삭제는 owner/superadmin만’ 정책은 확정 합주 등에서 유지한다. **본인 가용 시간 삭제·초기화는 사용자가 명시적으로 허용한 예외**다. 상태 삭제는 미정으로 되돌리며 기존 합주·업로드에는 영향을 주지 않는다. 본인의 가능 시간만 초기화할 때는 개인 메모를 지우지 않는다. owner의 밴드 전체 초기화는 위 확인 절차에 따라 메모까지 비운다.

## 데이터·API 설계 방향

- `BandAvailabilityDay`: band_id, membership_id, local_date, morning_status, afternoon_status, evening_status, updated_at, revision. 밴드·멤버·날짜 유일 제약, 각 상태의 AVAILABLE/UNAVAILABLE/UNKNOWN 제약과 멤버 band 정합성을 검증한다. 세 칸 고정이므로 임의 시간 구간 테이블은 만들지 않는다.
- 밴드별 조율 상태에 단조 증가 `generation`과 마지막 초기화 시각·수행자만 저장한다. 모든 저장·일괄 저장·초기화 요청은 현재 generation을 제출하고, 서버가 밴드별 조율 상태를 잠근 뒤 확인한다. 전체 초기화는 가용 자료·선택 메모 제거와 generation 증가를 한 트랜잭션으로 처리한다. 이전 generation 요청은 409로 거부한다. 삭제한 본문·옛 시간표의 회차별 사본을 별도로 보관하지 않는다. 감사 로그에는 수행자·시각·밴드·건수만 기록한다.
- 선택 개인 일정은 별도 `BandPersonalScheduleNote`에 작성자·밴드·날짜·선택 시간대·최대 200자 평문·공유 범위·revision을 보관하는 안이다. 날짜·시간대당 한 메모로 제한한다. 공유 범위 확정 후 최소 스키마를 확정하며, 비공개 일정 조회는 본인 전용 API로 분리한다. 집계는 본문을 읽지 않는다.
- 밴드 날짜 기준은 MVP에서 `Asia/Seoul` 고정이며 날짜는 DATE로 저장한다. 수정 시각 등 실제 시점은 UTC로 저장한다. 기기 현지 시간대 때문에 날짜나 오전·오후·저녁 선택이 바뀌지 않게 한다. 시간대에 숫자 범위를 붙일지는 UX에서 별도 확정하고, 정확한 합주 시각으로 자동 환산하지 않는다.
- 기존 `Rehearsal` 날짜·문자열 time 형식은 유지한다. 30분 단위·연속 시간 검색을 제외하므로 이번 MVP만을 위해 합주 시작·종료 타임스탬프를 새로 도입하거나 기존 합주 데이터를 변환하지 않는다.
- 초안 경로: GET `/api/v2/bands/{bandId}/availability?from=...&to=...`, PUT `/availability/me/{date}`, PUT `/availability/me/batch`, POST `/availability/candidates`, POST `/availability/reset`(owner 전용). reset은 기대 generation으로 중복 실행을 차단하며, 응답 유실 후에는 최신 generation과 초기화 기록을 조회해 결과를 확인하고 자동 재실행하지 않는다.
- 하루 세 상태를 원자적으로 저장하고 기대 revision으로 경합 시 409를 반환해 다른 기기의 수정을 덮어쓰지 않는다. 재전송은 멱등 처리한다. DELETE `/availability/me/{date}`는 본인 하루 상태를 미정으로 초기화한다. 초기화 후에도 단조 증가 revision을 유지해 이전 기기의 오래된 저장이 되살아나지 않도록 한다. 여러 날짜 일괄 초기화는 기간 제한·명시적 확인을 적용한다.
- 드래그 일괄 저장은 선택된 날짜·시간대만 수정하며 다른 칸과 메모는 보존한다. 1회 최대 42일×3칸으로 제한하고 중복 칸·잘못된 상태·다른 멤버 지정·오래된 generation/revision 중 하나라도 있으면 전부 거부한다. 날짜순 잠금과 단일 트랜잭션으로 일부만 저장되는 결과를 방지한다. UI 이벤트마다 요청하지 않고 저장 버튼당 한 요청으로 처리한다.
- 월 화면에 필요한 최대 42일 범위만 조회한다. 기간·조율 대상 수·본문·후보 수를 제한하고, 밴드·날짜·멤버 인덱스로 처리한다. 하루·시간 슬롯별 개별 HTTP 요청, 전체 회원의 전 기간 스캔, N+1 조회를 피한다.
- 기존 인증 클라이언트·band-scope·역할 검증·오류 형식·밴드 전환 시 요청 취소 규칙을 재사용한다. 최초 버전에는 WebSocket, 별도 큐, 상시 백그라운드 계산을 추가하지 않는다.

## 단계·커밋·검증

1. 확정된 세 시간대·선택 개인 일정·본인 초기화·owner 전체 초기화·드래그 일괄 입력 요구를 UX/API 계약에 반영한다. 개인 일정 공유 범위와 보관 기준 등 남은 선택을 확인한다.
2. BE 모델·migration·가용 시간 검증 및 권한 테스트. 기존 테이블 파괴적 변경은 하지 않는다.
3. BE 날짜별/일괄 저장·집계·후보 계산·owner 전체 초기화, generation/revision 경합·기간 제한 테스트.
4. FE 월별 요약·날짜별 멤버 3칸 표·드래그 일괄 선택·선택 개인 일정·모바일 대체 입력·owner 초기화 확인·재등록 안내·밴드 변경 격리. 기존 테마 토큰을 사용한다.
5. 기존 합주 생성 폼 연결·정확한 합주 시각 직접 입력·중복 저장 방지.
6. 전체 BE/FE 테스트·빌드·시각 검증. 각각 단위 커밋하며 구현은 서브에이전트, 총괄은 리뷰·검증을 담당한다.
7. 운영 DB 변경은 사용자 별도 승인 후 백업·복원 검증을 거쳐 적용한다. 이후 상시 승인 범위의 BE/FE 배포와 실제 API·권한·화면 확인을 수행한다.

필수 테스트: 두 밴드 교차 접근, 타인 시간표 변경 차단, 탈퇴 후 접근 차단·집계 제외, 미응답 가능 오인 방지, 전원 미응답, 하루 세 칸 독립 저장·부분/전체 초기화, owner만 전체 초기화 가능, 다른 밴드·확정 합주 보존, 메모 제거와 generation 전환의 원자성, 전체 초기화와 일괄 저장의 경쟁, 재시도·응답 유실 시 이중 초기화 방지, 초기화 후 오래된 저장 409, 드래그 선택 범위·취소·상한·부분 실패 없음·선택 밖 값 보존, 비공개 개인 일정 누출 방지·선택 공유·본문 평문 처리, 월 경계·윤일·KST, 동시 저장 409, 가용 시간 변경 후 확정 경고, 중복 합주 생성 방지, 기존 날짜 범위 합주 회귀, 모바일 스크롤/선택 충돌·키보드/터치 및 밴드 전환 중 지연 응답 차단.

## 이번 MVP에서 제외

- Google/Apple 등 외부 캘린더 연동·OAuth·동기화는 사용자 요청으로 완전히 제외한다. 추후 연동을 전제로 한 구조도 만들지 않는다. 다른 밴드의 일정 자동 충돌 확인도 하지 않는다.
- 30분 단위 시간표·연속 합주 시간 자동 검색, 반복 일정, 개인 일정의 상세 장소·첨부파일, 정교한 참석 투표·응답 마감, 푸시·메일 알림: 우선 세 시간대 입력과 후보 확인의 사용성을 검증한다. 선택적인 짧은 개인 일정 메모는 포함한다.
- R2 작업·미디어 재변환·스케일 변경, 보류한 정책 공표·필수 동의 활성화: 이 계획에 포함하지 않는다. 다만 가용 시간도 이용자 생활 패턴에 관한 자료이므로 실제 외부 공개 전에 개인정보 안내 범위를 다시 검토한다.

## 사용자 확정 및 남은 확인

확정: 개인 일정은 선택, 날짜별 오전·오후·저녁 세 칸, 본인 가능 시간은 직접 삭제·초기화 가능, owner가 밴드 전체 조율 일정을 초기화한 뒤 모두 다시 등록하는 흐름, 드래그 일괄 가능 설정, 외부 캘린더 연동 완전 제외.

구현 기본값: 선택 개인 일정은 비공개·명시적 밴드 공유이며 본인이 수정·삭제할 수 있다. 개인 일정 공유를 강제하거나 다른 밴드까지 공개하지 않는다. 자동 보관기한·주기적 삭제 작업은 추가하지 않으며, 본인 삭제 및 owner 전체 초기화로 조율 자료를 비운다. 실제 외부 공개 전 개인정보 안내·보관 기준 검토는 별도로 남는다.

## 구현 계약 보완

- 날짜별 상태는 AVAILABLE/UNAVAILABLE/UNKNOWN, 시간대 키는 morning/afternoon/evening이다. GET 응답에 현재 generation, 멤버/날짜별 revision, my_membership_id, can_reset을 제공한다. 모든 mutating API는 기대 generation을 필수 검증한다.
- 본인 날짜 초기화와 메모 삭제는 본문 없는 revision tombstone을 남겨 오래된 다른 기기의 재저장을 거부한다. 본인 메모 tombstone은 본문 없이 revision을 읽을 수 있게 하며 다른 멤버에게는 공개하지 않는다.
- owner 전체 초기화는 현재 밴드의 day/note 자료 삭제와 generation 증가를 같은 트랜잭션으로 처리한다. 이전 회차 원문 사본은 만들지 않는다. 감사 로그에 비공개 메모나 가용 상태 본문을 남기지 않는다.
- 후보 순위 계산은 이미 허용된 최대 42일 자료를 FE에서 계산한다. 후보 화면은 예약 보장이 아니며 합주 생성 전 최신 자료를 재확인한다. 합주 생성 자체는 기존 v2 권한·데이터 계약을 유지한다.
