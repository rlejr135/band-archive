# 24시간 초대 링크 구현 계약

작성일: 2026-10-19. 로컬 구현 기준이며 **운영 DB 적용·인증 설정 변경 승인이 아니다**.

## 범위와 상태

- 로고까지 운영 반영 완료. 이번 단위는 기존 계획 4단계 초대 링크이며 일반 가입 요청 화면 개편은 다음 단위다.
- BE·FE 담당 subagent가 구현하고 총괄이 리뷰·테스트·단위 커밋을 담당한다. 운영 반영은 DB 변경 내역과 검증 결과를 상세 보고한 뒤 별도 승인을 받는다.
- R2 객체, 기존 초대 코드 기록, 콘텐츠와 계정을 삭제하지 않는다. 메일 발송 설정·실제 가입 메일 발송·운영 가입 테스트는 실행하지 않는다.

## 데이터와 수명

- rev19를 고정한 뒤 rev20에서 `band_invite_link`, `invite_resume_context` 두 테이블만 추가한다. 이전 migration의 의미는 변경하지 않는다.
- 링크는 32바이트 난수의 canonical base64url 43자이고 DB에는 SHA-256만 저장한다. 서버 발급 시각부터 정확히 24시간, 여러 사용자에게 재사용 가능하며 owner/admin이 폐기할 수 있다.
- 복귀 식별자는 초대와 독립된 같은 강도의 난수이다. DB에는 해시와 예상 이메일의 HMAC만 저장한다. HMAC 키는 해당 원문 복귀 식별자, 메시지는 도메인 구분자와 서버 정규화 이메일이며 별도 비밀 설정을 추가하지 않는다.
- 복귀 기록은 발급 후 최대 1시간이며 초대 만료를 넘지 않는다. 이메일 확인이 늦어 만료되면 원래 초대 링크를 다시 여는 안내를 제공한다.
- 인증된 JWT의 확인된 이메일과 대조한 뒤 사용자 ID에 한 번 바인딩한다. 복귀 식별자만으로 가입하지 못하며 다른 사용자에게 다시 연결하지 않는다.
- 완료 후 응답 유실 재시도는 같은 활성 가입 결과만 반환한다. 완료 이후 탈퇴한 사용자를 재시도로 다시 가입시키지 않는다.

## API

모두 `/api/v2` 아래이며 초대·복귀 원문은 JSON body로만 보낸다.

| 경로 | 동작 |
| --- | --- |
| POST `/invite-links/preview` `{token}` | 제한된 공통 소개. 가입·프로필 생성 없음 |
| POST `/invite-links/resume-context` `{token,email}` | 이메일 확인/로그인 복귀 기록 발급. 가입 없음 |
| POST `/invite-links/resume` `{context}` | 인증·이메일·정책 확인 후 사용자 바인딩과 소개 반환. 가입 없음 |
| POST `/invite-links/accept` `{context}` | 명시적 확인 후 가입·프로필 보장 |
| GET/POST `/bands/{id}/invite-links` | 활성 owner/admin의 제한된 목록/새 링크 발급 |
| POST `/bands/{id}/invite-links/{id}/revoke` | 같은 권한으로 멱등 폐기 |

- 익명 POST 정책 예외는 preview와 resume-context에만 적용한다. 잘못된 Authorization을 익명으로 무시하지 않는다.
- 무효·만료·폐기·삭제된 밴드는 동일한 404, 요청 제한은 429, 인증/정책/서버 장애는 별도로 표시한다. 성공·오류 모두 private/no-store를 유지한다.
- 기존 코드 발급·가입·회전 등 경로는 새 기능 반영 시 410으로 종료하되 기존 행을 지우거나 새 링크로 변환하지 않는다.

## 접근·경쟁·남용 방지

- 유효한 초대가 비공개 밴드의 읽기 권한을 부여하지 않는다. 이름·소개 외 사진·공지·곡 통계는 실제 부모·자식 공개 범위로 제한하며 멤버용 R2 서명을 발급하지 않는다.
- 밴드 → 링크 → 복귀 기록 → 멤버십 → 프로필 순서로 잠근다. 가입 시 만료·폐기·계정 상태를 다시 검사한다.
- 활성 멤버는 중복 생성하지 않으며 pending/left/rejected는 일반 member로 활성화한다. 과거 admin 권한을 복구하지 않는다.
- 8KB 이하 body, canonical token, bounded IP/사용자별 요청 예산과 프로세스 전체 발급 예산을 적용한다. 프로세스 예산은 재시작·worker별로 독립적이며 분산 전역 제한이 아니다.
- 밴드 행 잠금 안에서 유효한 미완료 복귀 기록을 링크당 200개·밴드당 1,000개로 제한한다. 완료·만료 기록을 제외하므로 초대의 누적 사용 횟수 제한이 아니다. 만료 복귀 기록만 제한된 배치로 정리하고 감사 기록은 보존한다.
- 새 테이블도 기존 Flask 전용 접근/RLS·브라우저 권한 차단 계약을 유지한다. 구 SQLite refresh 도구는 새 capability 기록이 있으면 중단하도록 빈 테이블 검사를 추가한다.

## FE 인증 복귀

- `/invite#token=...`에서 React/AuthProvider 초기화 전에 초대 fragment를 제거한다. 원문은 메모리에만 유지하고 query·localStorage·분석·로그로 보내지 않는다.
- 로그인/회원가입은 고정 `/invite/continue`로 복귀한다. 일반 `safeReturnPath`의 `/bands` 제한은 확장하지 않고 초대용 정확한 경로만 별도 허용한다.
- 이메일 콜백은 `/verify-email?invite_resume=<복귀 식별자>`를 사용한다. 이 식별자만 필요한 경우 단기 sessionStorage에 보관할 수 있으며 초대 원문은 저장하지 않는다.
- 콜백의 복귀 marker만 제거하고 Supabase의 code/auth fragment는 SDK가 처리하기 전에 지우지 않는다. 미리보기·로그인 완료·이메일 확인만으로 가입하지 않는다.
- 문서 referrer 차단과 초대 화면의 외부 요청 최소화를 적용한다. 식별자가 없어졌거나 확인이 지연되면 원래 링크 재방문을 안내한다.
- Supabase 공식 [리디렉션 안내](https://supabase.com/docs/guides/auth/redirect-urls)와 [현재 공개 구현](https://github.com/supabase/auth/blob/master/internal/utilities/request.go)은 같은 Site URL origin의 리디렉션을 허용한다. 따라서 현재 Pages Site URL에서 위 query 콜백은 설정 변경 없이 동작할 것으로 추론한다. **운영 제공자의 실제 버전·메일 템플릿을 통한 왕복은 아직 검증하지 않았다.** 설정 변경이 필요하면 별도 승인받는다.

## 검증·승인 관문

- 두 밴드·두 계정, 권한표, 만료 경계, 잘못된 토큰/계정, 공개 범위·서명 미발급, 정책 gate, 동일 사용자 중복/탈퇴 후 재시도, 폐기 경쟁과 프로필 원자성을 검증한다.
- 과거 스키마 snapshot, rev19→20 보존·권한, 전체 BE·FE 회귀 테스트, lint/build, 로컬 브라우저 mock 흐름을 검증한다.
- 실제 운영 DB 변경 전 추가 테이블·인덱스·외래 키·백업/복구/보존 검증 결과를 보고하고 사용자 승인을 다시 받는다. 승인 전에는 새 DB head를 요구하는 BE나 새 초대 UI를 운영 배포하지 않는다.
