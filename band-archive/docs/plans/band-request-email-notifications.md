# 밴드 생성 요청 승인·거절 이메일 알림 계획

- 작성일: 2026-10-14
- 상태: 사용자 승인으로 통합 계획의 단계별 구현에 포함한다. 운영 DB 변경·SMTP 비밀 설정·실제 메일 발송·push·배포는 별도 승인 전까지 실행하지 않는다.
- 통합 계획: [band-profile-and-design-system.md](band-profile-and-design-system.md). 구현은 subagent가 담당하고 main agent가 검토·검증·단위별 커밋한다.

## 목표

플랫폼 관리자가 밴드 생성 요청을 승인하거나 거절하면 요청자의 인증된 계정 이메일로 결과를 알린다. 광고·마케팅 메일은 포함하지 않는다.

## 현재 상태

- `band_service.review_request()`는 요청 상태, 검토 메모, 감사 로그를 저장한다.
- 승인 시 밴드와 요청자의 활성 소유자 멤버십을 생성한다.
- 결과 이메일 및 요청자용 처리 결과 목록은 아직 없다.
- 기존 Supabase SMTP 설정은 인증 이메일용이다. Flask가 해당 설정을 자동으로 가져오거나 인증 이메일 API를 승인 알림 용도로 사용하지 않는다.

## 발송 방식 및 운영 준비

- 소규모 초기 운영은 기존 Gmail SMTP 계정을 활용하는 방향으로 검토한다. 별도 메일 서비스 구독은 필요하지 않을 수 있으나 발송 제한·차단·전달률 및 기존 인증 메일과 공유하는 계정 한도를 구현 시 재확인한다.
- 발신 계정 사용 승인을 받고 SMTP host/port/user/app password/from 등 필요한 값만 서버 비밀 설정에 등록한다. 저장소·프론트·문서·로그에 비밀번호를 넣지 않는다.
- 사용자 확인 임시 발신·문의 주소는 `rlejr135@gmail.com`이다. 발신 주소·문의 주소·서비스 표시 이름은 별도 서버 설정으로 분리해 정식 이름/이메일 확정 후 교체할 수 있게 한다. 실행 코드와 프론트에 개인 이메일을 하드코딩하지 않으며 예시 환경 파일은 가짜 주소를 사용한다. 테스트 수신자는 아직 미확정이며 실제 테스트 메일 발송은 수신자와 목적을 확인한 뒤 진행한다.
- 인증된 계정 이메일을 서버에서 조회하며 관리자 요청 body에 임의 수신 주소를 받지 않는다. 계정 삭제·비활성·이메일 변경 시 수신 대상 정책을 정한다.
- 발송량이나 전달 문제가 증가하면 전문 발송 서비스로 교체한다. 유료 플랜·도메인 구매·공급자 변경은 별도 승인 사항이다.

## 메일 내용

- 제목: `[Band Archive] 밴드 생성 요청이 승인되었습니다` 또는 `거절되었습니다`.
- 본문: 밴드 이름, 결과, 검토 메모가 있는 경우 그 내용, 운영 사이트 링크.
- 승인 링크는 고정 운영 origin과 서버가 관리하는 slug로 만든다. 거절 링크는 내 계정의 요청 결과 화면을 사용한다.
- HTML을 사용하면 이름·메모를 escape하고 plain-text 본문도 제공한다. 메일 헤더 개행 삽입을 차단한다.
- 초대 코드, JWT, 비밀번호, 다른 이용자의 정보는 넣지 않는다.

## 구현 구조

1. DB outbox 테이블에 요청 ID, 결과, 발송 상태, 시도 횟수, 다음 시도 시각 및 필요한 최소 정보를 저장한다.
2. 승인·거절 상태 변경과 outbox 생성을 같은 트랜잭션으로 커밋한다. 이미 처리된 요청의 재호출은 추가 메일을 만들지 않는다.
3. 고유 제약으로 요청별 결과 이벤트를 중복 생성하지 않는다. 메일 실패가 승인·거절을 되돌리지 않도록 한다.
4. 트랜잭션 밖에서 워커가 발송한다. 다중 워커 작업 잠금, 제한된 동시성, SMTP TLS·timeout, 지수 backoff 및 최대 재시도를 적용한다.
5. 재시도 소진 시 실패 상태로 남기고 관리자에게 표시하며 수동 재시도를 제공한다. 이메일 주소·본문·인증정보 대신 이벤트 ID와 안전한 오류 분류만 로그에 남긴다.
6. SMTP 수락 직후 프로세스 종료 등의 경우 중복 전달 가능성이 있으므로 정확히 한 번 전달을 보장한다고 주장하지 않는다. outbox 중복 생성 방지와 실제 전달 보장은 구분한다.
7. 요청자용 생성 요청 목록을 내 계정에 추가해 승인·거절·검토 메모를 확인하게 한다. 메일 미수신·스팸 분류 시에도 결과를 확인할 수 있어야 한다.

## 단계와 커밋

1. 결과 알림 계약·수신 정책·테스트와 outbox migration.
2. 승인·거절 서비스의 원자적 이벤트 생성 및 재호출 멱등성.
3. SMTP 발송·워커·재시도·실패 관측.
4. 요청자 결과 화면과 관리자 발송 실패 표시·재시도 권한.
5. 격리 전체 테스트 → 별도 승인 후 운영 migration·비밀 설정 → BE/FE 배포 → 승인된 테스트 수신자에게 전달 확인.

각 단위는 별도 커밋한다. 구현 단계에서 기존 계획의 DB migration·배포·비밀 설정 승인 범위를 다시 확인한다.

## 검증

- 승인·거절 각각 올바른 요청자에게만 전송하며 플랫폼 관리자만 처리·재시도할 수 있다.
- 중복·동시 승인, 트랜잭션 rollback, SMTP timeout, 워커 종료·재실행 및 재시도 소진을 검증한다.
- 메일 실패 시 승인된 밴드·소유권이 유지되고 중복 이벤트가 생성되지 않는다.
- 계정 비활성·삭제·이메일 변경, 잘못된 주소, 제목 개행·HTML 삽입을 검증한다.
- 요청자 목록은 본인 요청만 조회하며 다른 사용자·밴드 데이터나 내부 발송 오류를 노출하지 않는다.
- 테스트는 모의 SMTP 또는 승인된 별도 수신자를 사용하며 자동 테스트에서 실제 메일을 보내지 않는다.
