# 밴드 로고 기능 — 운영 DB 적용 전 검토

작성일: 2026-10-18 (KST)
최종 결과 확인: 2026-10-19 (KST)

상태: 사용자 승인 후 백업·앱 영역 복구·데이터 보존 검증 및 운영 DB rev19 적용 완료. BE Fly v61 및 FE Cloudflare Pages 운영 반영·HTTP/CORS/번들 검증 완료(2026-10-19). 초대 링크 스키마는 이번 로고 변경에 포함하지 않는다.

## 변경할 내용

- Alembic `20261017_18` → `20261018_19`.
- `band_logo` 연결 테이블 추가: `band_id` 기본 키와 밴드 외래 키, `gallery_image_id`, 같은 밴드의 사진만 허용하는 복합 외래 키.
- `gallery_image(band_id, id)` 고유 인덱스 `uq_gallery_image_band_id` 추가. 기존 사진 행은 수정하지 않는다.
- 새 테이블은 빈 상태로 생성한다. 기존 밴드 로고를 임의로 지정하거나 사진을 복사하지 않는다.
- 사진/밴드 삭제 시 로고 연결 행만 함께 제거한다. 로고 해제 자체는 사진이나 R2 파일을 삭제하지 않는다.
- 로고 선택이 존재하면 downgrade는 중단한다. 자동으로 선택 정보를 버리지 않는다.

## 권한과 화면

- owner 또는 활성·이메일 인증 완료 superadmin만 선택·해제한다. 일반 멤버와 밴드 admin은 변경할 수 없다.
- 별도 로고 관리 API와 화면만 사용한다. 비멤버 superadmin의 로고 관리 권한으로 일반 비공개 밴드 화면·명단·초대 관리 권한을 열지 않는다.
- 비공개 사진 URL은 최대 300초로 서명한다. 다른 밴드 사진과 삭제 대기 사진은 선택할 수 없다.
- 상단 로고의 사진 없음·접근 불가·만료 갱신 실패 시 중립 기본 표시를 사용한다.
- 대표 사진 선택과 로고 선택은 독립적이다. 전용 새 파일 업로드·크롭은 추가하지 않는다.

## 검증 결과

- FE 전체 테스트 294개 통과, 변경 JavaScript lint 및 운영 빌드 통과. 기존 큰 번들 경고는 남아 있다.
- 실제 로컬 샘플에서 선택·해제 동작과 320px 모바일 배치를 확인했다. 샘플 요청은 모의 처리하며 운영 API/DB를 호출하지 않는다.
- 격리된 로컬 PostgreSQL 18→19 정상 변경 및 보안 오염 차단 테스트 2개 통과: 기존 갤러리 행·파일 키 보존, 빈 로고 테이블, RLS/접근 권한 확인; 정책·PUBLIC/상속 권한·시퀀스 권한·기본 권한 이상 시 DDL 전 중단 확인.
- BE 권한·동일 밴드 제약·삭제 대기·서명 실패·이전 스키마 보존 테스트를 포함한 전체 pytest가 933개 모두 통과했다(770.89초, 경고 924개). 경고는 최종 로그에 남아 있으며 모두 해결했다고 주장하지 않는다.
- 첫 전체 실행은 926개 통과·6개 실패였다. 실패 원인은 기존 데이터 이전/보존 도구의 정확한 표 목록에 새 테이블이 누락된 것이었다. `band_logo`를 명시적으로 관리 목록에 포함하되 선택 행이 있으면 이전을 거부하도록 수정했다. 관련 SQLite/PostgreSQL 모듈 재검증 9개 통과 후 전체 실행 933개 통과를 확인했다.
- 로고 선택과 갤러리 삭제가 같은 밴드 잠금 순서를 사용하는 것을 코드 리뷰로 확인했다. 실제 병렬 API 경쟁 상황을 새 테스트로 재현하지는 않았으며, 이 항목을 자동화 테스트 완료로 주장하지 않는다.

최종 소스 `1b2b7b0`의 전체 BE 재검증: 933개 통과(609.36초, 경고 924개). 근거: `backend/tools/.state/validation-20261017-f1c9a36803a1491ca45ad46c12b3f613/stdout.log`, SHA-256 `0e3b6eab08d96c0b99a2f186953a61e871fffdc68f0f6375b838495f6517f5ed`.

## 운영 복구 리허설 중 확인한 호환성 보완

- 같은 read-only repeatable-read 스냅샷에서 전체 접근 가능 DB 아카이브와 public 앱 영역 아카이브를 모두 만들었다. 전체 아카이브 SHA-256: `701e754da0650dfb4c36324643345b068423f63128fc03ed0c105d4bb5ff3cea`; public 아카이브: `19eeb4b7ec7be23f71bc4419f83f344ff172eb996bf2e01f779a01be00e8271f`.
- 비공개 로컬 PostgreSQL 복구본의 기존 앱 테이블 34개 행 해시·카탈로그·소유자·권한·정책·역할 연결이 원본과 일치했다. 복구 범위는 public 앱 영역이며 Supabase 관리 Auth/Storage 서비스 자체의 복구 검증은 아니다.
- 첫 로컬 변경 시 rev19가 실제 생성자와 무관한 Supabase 관리 역할의 기본 권한까지 검사해 중단됐다. 운영 DB는 변경되지 않았다.
- PostgreSQL은 새 객체에 현재 생성자 역할의 기본 권한만 적용한다. 멤버로 속한 다른 역할의 기본 권한은 상속되지 않는다. [PostgreSQL 17 공식 문서](https://www.postgresql.org/docs/17/sql-alterdefaultprivileges.html)
- 미적용 rev19 쿼리에 `defaclrole=current_user::regrole`을 추가해 기존 rev14/rev17·서버 시작 검증과 범위를 일치시켰다. 기존 마이그레이션·운영 기본 권한은 변경하지 않았다. PUBLIC/클라이언트·상속 권한·테이블/시퀀스·전역/public 기본 권한 차단은 유지한다.
- 호환성 보완 검증: 마이그레이션·보안 관련 67개 통과, 최종 보강 PostgreSQL 테스트 2개 재실행 통과, 전체 BE 933개 통과. 다른 생성자 역할에 가입해도 새 로고 테이블이 postgres 소유이고 브라우저 역할의 8가지 테이블 권한이 모두 거부됨을 확인했다. 실제 앱 생성자의 위험한 기본 권한은 계속 거부한다. 수정 소스의 복구 리허설까지 통과한 뒤에만 운영에 적용했다.

## 승인 후 적용 절차

1. 대상 DB와 현재 revision을 확인하고, TLS 검증을 유지한 전체 DB 백업을 보호된 로컬 경로에 저장한다. 비밀번호·DSN을 출력하지 않는다.
2. 백업 SHA-256 및 archive 목록을 확인하고 별도 로컬 PostgreSQL에 복구한다. 테이블별 건수·관계 무결성·R2 key 컬럼의 해시 대조로 보존 여부를 확인한다.
3. 복구본에서 migration을 적용해 변화가 빈 연결 테이블과 인덱스·제약으로 한정되는지 확인한다. 기존 테이블의 건수와 파일 키는 같아야 한다.
4. 운영 DB의 RLS·소유자·클라이언트/상속 권한·정책·기본 권한 사전 검사 후 한 번만 적용한다. 예상과 다르면 중단하고 보고한다.
5. BE 배포 → API 확인 → FE push·배포 → 실제 번들·HTTP·CORS 확인 순으로 진행한다. 실패 시 자동 downgrade하지 않는다.

운영 DB 변경은 별도 승인을 받은 뒤에만 수행하며, 백업/복구 검증이 실패하면 적용하지 않는다. 초대 링크·가입 복귀 기록 변경은 별도 구현·검증·보고 대상이다.

고유 인덱스 및 제약 생성 중 `gallery_image`에 ACCESS EXCLUSIVE 잠금을 사용한다. 실제 실행 시간은 운영 데이터 규모에 따라 달라지며 갤러리 조회·업로드가 잠시 대기할 수 있다. 운영 적용 전 트랜잭션/잠금 타임아웃을 검토하고 장시간 대기하면 중단하며, 무조건적인 재시도나 권한 검사 우회는 하지 않는다.
