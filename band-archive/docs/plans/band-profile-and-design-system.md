## 1. 현재 원인과 작업 범위

- 메인 `WelcomeLanding.css`는 어두운 녹색 배경 `#111512`, 밝은 본문, 라임 강조색 `#d1ed7b`를 사용한다. 계정 `BandsPage.css`도 비슷한 색을 별도 하드코딩한다.
- 밴드 `BandWorkspace.css`와 관리 화면의 `.bands-page`는 `index.css`의 파란 회색 배경과 노란 강조색을 사용한다. 버튼·카드·테두리·hover 규칙이 화면별로 나뉘어 있다.
- 관리 화면은 별도 라우트이며 `BandOnboarding.jsx`의 복귀 `<Link>`에 버튼/이동 링크 클래스가 없어 기본 링크로 표시된다.
- 밴드 `description` 컬럼과 조회는 이미 있지만 수정 API와 폼이 없다. 기존 관리자용 `can_edit`는 owner/admin 모두 true여서 소개의 owner 전용 권한 판단에 그대로 사용할 수 없다.

계획 승인 후 구현 범위는 소개 편집·복귀 링크·공통 디자인 통일·밴드 생성 승인/거절 메일 알림·영상 삭제 권한 제한이다. 색상 테마를 위한 공통 토큰/적용 경계까지만 준비하고, 실제 밴드별 선택·저장 UI는 후속 단계로 둔다.

## 2. Owner 전용 밴드 소개 편집

### API·권한

- 신규 `PATCH /api/v2/bands/{bandId}/profile`에 정확히 `{ "description": "..." }`만 허용한다. 이름·slug·소유자·멤버십·공개 범위 등 다른 필드를 함께 변경하지 않는다.
- 인증된 사용자와 해당 밴드의 활성 owner 멤버십만 허용한다. admin·일반 멤버·가입 대기·탈퇴·플랫폼 관리자 단독 권한으로는 수정할 수 없다.
- 기존 중앙 권한 helper와 트랜잭션을 재사용해 소유권 이전/탈퇴와 경합할 때 쓰기 시점 권한을 다시 검사한다. 존재하지 않거나 접근할 수 없는 밴드는 기존 보호 API의 404 정책을 따른다.
- `band_dict`에 `permissions.can_edit_band_profile`을 추가한다. FE는 역할 문자열이나 기존 포괄 `can_edit`로 권한을 추측하지 않는다.
- 소개는 plain text, 최대 2,000자, 문자열만 허용한다. 앞뒤 공백을 정리하고 빈 문자열은 NULL로 저장하여 소개를 지울 수 있게 한다. HTML/Markdown 실행이나 추가 외부 요청은 하지 않는다.
- 기존 `description` 컬럼을 사용하므로 이 단계에 schema migration은 필요 없다. 감사 로그에는 변경 필드만 기록하고 소개 원문은 넣지 않는다. 응답은 서버 권한이 포함된 `{ band: ... }`로 한다.

### 관리 화면

- `밴드 관리 → 기본 정보 → 밴드 소개` 섹션을 추가한다. owner에게만 수정·저장·취소와 글자 수를 제공한다. 다른 밴드 관리자에게는 필요 시 읽기 전용으로 표시한다.
- 저장 중 중복 요청을 막고, 실패 시 입력을 보존한다. 403 등 권한 해제 시 편집을 닫고 관리 화면의 기존 접근 제한 정책에 맞춰 권한을 재확인한다.
- 밴드/계정 변경 및 unmount 시 요청을 취소하고 늦게 도착한 응답을 무효화한다. 성공 응답으로 현재 소개를 갱신하고 관련 밴드 요약/조회 캐시만 갱신한다.
- 이전 밴드 설명이 새 밴드에 섞이거나 프로필 갱신 때문에 업로드 작업/재생기가 불필요하게 초기화되지 않게 한다.
- `Imported legacy archive; ownerless until claimed.`는 owner가 지우거나 실제 소개로 교체할 수 있다. 이번 구현에서 임의로 운영 DB를 일괄 수정하지 않는다.

## 3. 관리 화면 복귀 링크 정리

- 문구는 `밴드 공간으로 돌아가기`로 정리하고 작은 좌측 화살표를 보조 아이콘으로 둔다. 이동이므로 HTML button이 아닌 Router Link 의미를 유지한다.
- 공통 이동 링크/secondary action 스타일을 사용해 높이·패딩·테두리·hover·focus·아이콘 간격을 맞춘다. 헤더의 제목/브레드크럼과 함께 배치하고 본문 카드와 간격을 둔다.
- 알려진 현재 밴드 slug의 canonical `/bands/{slug}`로 이동한다. 브라우저 history의 뒤로 가기는 사용하지 않아 외부 페이지나 다른 밴드로 돌아가는 문제를 피한다.
- 키보드 포커스가 보이고 모바일에서 누르기 쉬워야 한다. 접근 불가 화면의 `내 밴드로 이동` 링크도 같은 이동 컴포넌트 규칙을 사용한다.

## 4. 메인과 밴드 공간의 디자인 통일

### 공통 원칙

- 메인의 짙은 녹색·라임 계열을 기본 제품 스타일로 삼는다. 랜딩은 소개용 큰 타이포그래피를, 작업 공간은 정보 중심 밀도를 유지하되 같은 제품으로 보이게 한다.
- 공통화 대상: 색상 의미, 글꼴/타이포 계층, 여백 척도, 카드 라운드/테두리/그림자, 버튼/링크/폼/오류·빈 상태, focus·hover·disabled 상태.
- 랜딩 미리보기는 계속 합성 예시이고 실제 밴드 데이터를 요청하지 않는다. 로그인 전 밴드 탭을 숨기는 기존 UX와 권한은 유지한다.
- 단순히 전역 색상 몇 개만 바꾸거나 기존 CSS 위에 화면별 override를 계속 덧붙이지 않는다. 중복 토큰과 공통 표현을 작은 단위로 추출하고 현재 사용처를 순서대로 전환한다.

### 구조

- 공통 semantic 토큰 파일을 둔다: `background`, `surface`, `surface-raised`, `text`, `text-muted`, `border`, `accent`, `accent-hover`, `on-accent`, `focus-ring`, `danger`, `success` 등.
- radius·spacing·shadow·type scale은 색상 토큰과 분리해 제품 공통 규칙으로 유지한다. hover 색과 강조 배경의 글자색을 항상 한 쌍으로 정의한다. 기존 흰색 hover 및 밝은 배경 위 흰색 글자 같은 규칙도 정리한다.
- 기존 `--primary-color` 등은 전환용 alias로 연결할 수 있지만 새 토큰을 단일 원천으로 두고 중복 palette 선언은 제거한다.
- 공통 shell/header/card/action 스타일 또는 작은 presentational 컴포넌트를 만든다. 계정과 밴드의 메뉴·권한·데이터 요청 로직까지 무리하게 한 컴포넌트에 합치지 않는다.
- 헤더에는 같은 제품 브랜드/시각 규칙을 적용하고, 밴드 공간에는 서버가 반환한 밴드 이름과 밴드 메뉴를 별도로 표시한다. 밴드 로고 업로드/브랜딩 커스터마이즈는 이번 범위가 아니다.
- 관리 페이지도 밴드 공간과 같은 표면·폭·헤더/액션 규칙을 사용한다. 기존 관리 권한 검증 완료 전에 밴드 정보/관리 내용을 표시하지 않는다. 화면 통합으로 API 조회를 중복 생성하지 않는다.
- 대시보드, 곡, 합주, 멤버, 갤러리, 추천, 관리에 적용한다. 계정·검색·생성 요청·인증 화면은 공통 토큰/기본 컴포넌트로 연결하되 권한별 동선은 유지한다.
- 모바일의 한 줄 가로 스크롤 탭과 PC의 정보 밀도를 유지한다. 사진 비율 보존과 달력/업로드/플레이어 기능을 바꾸지 않는다.

## 5. 후속: 밴드별 색상 조합

이번에는 토큰 경계만 만들고 아래 기능은 나중에 별도 승인 후 구현한다.

- 큰 틀·레이아웃·글꼴·컴포넌트는 고정하고 색상 조합만 변경한다.
- 초기에는 대비와 상태별 표시를 검증한 몇 가지 preset을 권장한다. 예: 기본 라임, 블루, 퍼플. 자유 RGB 입력·사용자 CSS/JS·외부 stylesheet 주소는 받지 않는다.
- owner가 선택하고 밴드 구성원에게 공유되는 밴드 설정으로 저장하는 방향을 우선안으로 둔다. 관리 권한 확대가 필요하면 후속 구현 전 사용자에게 확인한다.
- 서버에는 palette 값 전체 대신 검증된 `theme_key`를 저장하고 조회 응답에 포함한다. 기본값/기존 밴드 fallback은 공통 기본 테마다. 컬럼 추가·migration은 이 후속 단계에서만 수행한다.
- CSS 변수는 해당 밴드 컨테이너에만 적용한다. `document.documentElement`를 직접 바꾸어 내 계정/로그인/다른 밴드로 색이 누출되지 않게 한다. 관리 화면도 동일한 밴드 테마를 따른다.
- 계정/밴드 전환 중에는 기본 테마와 loading 상태를 사용하고, 이전 밴드 테마가 먼저 표시되지 않게 한다. 알 수 없는 theme key는 안전한 기본값으로 처리한다.
- 색상 변경으로 컴포넌트 key나 업로드/재생 상태를 재생성하지 않는다. 저장 취소·미리보기·기본 테마 복귀는 후속 UI에서 제공한다.
- 위험/성공/선택 상태는 색만으로 전달하지 않고 텍스트·아이콘도 유지한다. 각 preset의 본문, 버튼, 링크, 포커스, 오류 및 달력 선택 상태를 검증한다.

## 6. 함께 진행할 승인·거절 메일 알림

- 플랫폼 관리자가 밴드 생성 요청을 승인/거절하면 요청자의 인증된 계정 이메일에 결과·밴드 이름·검토 메모·운영 사이트 링크를 보낸다. 밴드 가입 요청 승인 메일이나 광고 메일은 이번 범위가 아니다.
- 초기에는 기존 Gmail SMTP 활용을 검토한다. Supabase의 인증 SMTP 설정을 Flask에서 자동으로 재사용하는 기능은 없으므로 별도 서버 발송 설정이 필요하다.
- DB outbox 생성과 처리 결과 저장을 한 트랜잭션으로 수행하고, 별도 발송 워커가 SMTP timeout·한도·재시도를 처리한다. 메일 실패가 밴드 승인/소유권을 취소하지 않게 한다.
- 중복 처리 요청은 새 발송 이벤트를 만들지 않는다. SMTP 수락 후 장애 등으로 인한 중복 전달 가능성은 남을 수 있으므로 정확히 한 번 전달을 보장하지 않는다.
- 요청자는 내 계정의 생성 요청 결과 목록에서도 상태·검토 메모를 확인한다. 플랫폼 관리자는 발송 실패 상태와 수동 재시도를 관리한다.
- 임시 발신·문의 주소는 `rlejr135@gmail.com`으로 사용자 확인을 받았다. 발신 주소·문의 주소·서비스 표시 이름은 별도 서버 설정으로 분리하며 개인 주소를 실행 코드에 하드코딩하지 않는다. 테스트 수신자·실제 발송은 아직 미승인이다. 비밀번호는 채팅/저장소에 넣지 않는다. 운영 migration, 비밀 설정 등록, 실제 테스트 메일 및 배포는 각각 승인 범위를 확인한다.
- 기존 오디오 추출 큐와 메일 큐는 목적/재시도 정책을 분리한다. SMTP 실패가 영상 처리나 API 요청을 오래 점유하지 않도록 제한한다.

## 7. 영상 삭제 권한: owner 또는 superadmin

- 저장이 완료된 영상 콘텐츠 삭제는 해당 밴드의 활성 owner 또는 서버 DB에서 확인된 활성·인증된 superadmin만 허용한다. 일반 멤버·band admin·업로더 본인이라는 이유만으로 영상 삭제를 허용하지 않는다.
- 곡/합주 미디어와 멤버의 개인 기록 영상에 같은 정책을 적용한다. 독립 음원·사진·댓글 삭제 권한은 이번 요청으로 확대하거나 변경하지 않는다. 미완료 업로드 취소/임시 파트 정리는 완성된 영상 삭제와 구분한다.
- FE의 서버 `can_delete`와 실제 삭제 API를 함께 변경한다. 버튼 숨김만으로 구현하지 않고 객체의 실제 band_id·file_type·현재 권한을 서버에서 검사한다.
- superadmin 예외는 영상 운영 삭제에만 한정한다. 중앙 밴드 권한 helper를 포괄 우회해 다른 밴드의 모든 조회/수정 권한을 열지 않는다. 밴드 비회원 superadmin의 삭제 진입점은 별도 운영 권한 경로로 설계하고 감사 로그를 남긴다.
- 곡·합주·멤버/개인 기록 삭제가 영상을 연쇄 삭제할 수 있는 경로도 점검한다. 영상 삭제 권한이 없는 사람이 부모 삭제를 통해 우회할 수 없도록 제한하거나 안전하게 차단한다.
- 허용된 개별 영상 삭제에서는 기존 삭제 서비스의 관련 영상 객체·추출 M4A·DB 연결 정리 계약을 재사용하고, 공유 키·다른 밴드 객체를 잘못 지우지 않게 검증한다. R2/DB 중 한쪽만 실패한 경우의 재시도·멱등성도 확인한다.
- 사용자 삭제 확인과 작업 중 중복 요청 차단을 둔다. 계정/소유권 변경·늦은 응답·다른 밴드 ID·superadmin 권한 해제 등을 테스트한다. 실제 운영 영상은 구현/자동 테스트 중 임의로 삭제하지 않는다.
- 이 정책은 이번 계획에 포함한다. 저장된 모든 영상을 일괄 교체/삭제하거나 재변환하는 운영 작업은 계속 별도 범위다.

## 8. 실행 순서와 커밋

1. **소개 API 계약·권한 테스트:** 기존 Band 컬럼·중앙 owner 검증 재사용. 커밋 `Add owner-only band profile editing`.
2. **소개 관리 폼:** owner 표시·저장/취소·늦은 응답·설명 삭제 및 캐시 갱신. 커밋 `Add band description editor to management`.
3. **공통 디자인 기반:** 제품 기본 토큰/공통 action·card·shell 스타일 추출, 기존 alias 전환. 커밋 `Establish shared archive design tokens`.
4. **복귀 링크 및 관리 화면:** 공통 이동 링크와 헤더/본문 적용. 커밋 `Align band management navigation and layout`.
5. **밴드 공간/계정 디자인 통일:** 화면별 중복 색/버튼 규칙 전환, 기존 기능 유지. 범위가 크면 shell·콘텐츠 화면 커밋을 나눈다.
6. **메일 알림 기반:** 결과 이벤트 계약·outbox migration·원자적 이벤트 생성·SMTP 발송/재시도/실패 관측을 단위별 커밋으로 구현한다. 상세 순서는 메일 계획서를 따른다.
7. **요청 결과·발송 상태 UI:** 요청자 본인 결과 조회, 플랫폼 관리자 발송 실패 표시/재시도 화면을 공통 디자인으로 구현한다.
8. **영상 삭제 권한:** owner/superadmin 전용 서버 검사·FE 삭제 표시·관련 연쇄 삭제 우회 방지·모의 R2 실패/멱등성 회귀를 BE/FE 단위로 커밋한다.
9. **전체 검증:** BE pytest, FE 전체 tests·변경 파일 lint·운영 build, PC/모바일 시각 검증 및 모의 SMTP 실패·중복·경쟁 조건 검증. 구현은 BE/FE subagent, 메인은 권한·diff·회귀 검토와 단위별 커밋 취합을 담당한다.
10. **배포:** outbox용 운영 migration·SMTP 비밀 설정·push/배포의 승인 범위를 확인하고 BE → origin/master 일반 push → Cloudflare 순으로 진행한다. 사용자 승인 후 지정한 테스트 수신자에게 전달을 확인한다. 배포 자체에서 운영 R2 파일을 삭제/변환하지 않으며 Fly 스케일 변경·기존 데이터 재이전도 포함하지 않는다.

실제 밴드별 테마 선택·DB 저장·migration·배포는 위 5절을 별도 구현 단계로 계획한다.

### 영상 삭제 구현 전 확인한 안전 조건

- 기존 객체 삭제 helper는 저장된 canonical object key를 모두 반영하지 않아 그대로 재사용하지 않는다. 원본/720p/M4A 키와 legacy fallback을 서버에서 정규화·검증하고 두 미디어 테이블의 공유 참조를 확인해야 한다.
- R2와 DB는 하나의 원자적 트랜잭션이 아니다. 삭제 중 일부 객체만 정리되거나 DB 커밋이 실패해도 재시도할 수 있도록 삭제 대기 상태와 지속성 있는 작업 기록을 설계한다. 이 추가 스키마는 영상 삭제 구현 단위에서 검증한다.
- 영상이 남은 부모 곡/합주/멤버 삭제는 명시적인 영상 삭제를 먼저 요구하는 방식으로 우회를 차단한다. 레거시 v1 쓰기가 켜져 있어도 같은 안전 경계를 적용한다. 독립 음원/사진의 기존 권한은 유지한다.

## 9. 검증과 완료 기준

- 두 사용자·두 밴드로 owner만 자기 밴드 소개를 변경할 수 있는지 검증한다. admin/멤버/플랫폼 관리자 단독·비활성 계정·가입 대기·탈퇴·잘못된 밴드 ID를 포함한다.
- 2,000자 경계·빈 문자열 삭제·비문자열/알 수 없는 필드 거부·HTML escape·소유권 이전과의 경쟁·실패 시 rollback을 검증한다.
- 입력 보존, 취소, 중복 저장 방지, 403, 늦은 성공/실패 응답, 계정/밴드 전환, 저장 후 홈에 새 소개 표시를 검증한다.
- 복귀 링크의 실제 경로·키보드 포커스·모바일 터치 영역을 확인한다.
- 메인/계정/밴드/관리에서 동일한 색상·기본 컴포넌트 규칙을 쓰는지, 좁은 화면·긴 밴드 이름·장문 소개·빈 사진·오류 상태에서도 가로 넘침/잘림이 없는지 확인한다.
- 공통 스타일 변경으로 로그인 전 탭 노출, 교차 밴드 데이터, 영상/라디오 모드, 투표, 업로드 대상 혼합이 발생하지 않아야 한다.
- 승인·거절 메일의 올바른 수신자, 중복 이벤트 방지, SMTP 장애/워커 재시작/재시도 소진, 권한 없는 수동 재시도 차단, 메일 실패 시 승인 상태 보존을 검증한다. 자동 테스트는 실제 발송하지 않는다.
- 요청자 결과 목록은 본인 요청만 노출하며 메일 주소·본문·비밀번호·내부 오류를 로그나 다른 사용자 응답에 노출하지 않는다.
- 저장된 영상의 직접/부모 연쇄 삭제에 같은 권한 경계가 적용되는지, 일반 멤버·band admin·업로더가 우회할 수 없는지, 독립 음원/사진의 기존 권한이 보존되는지 검증한다. 운영 R2가 아닌 모의 저장소를 사용한다.
- 시각 검증을 도구로 수행할 수 없으면 통과로 보고하지 않는다. 사용자 캡처/로컬 브라우저 확인 등 가능한 경로를 요청하고 미완료로 구분한다.

## 10. 이번에 제외하는 사항과 이유

- **밴드 이름/slug 변경:** 이름 변경은 표시 명칭을, slug 변경은 밴드 URL을 바꾼다. slug에는 링크/딥링크·리다이렉트·중복 정책이 필요하다. 소개 편집과 다른 계약이므로 이번에 혼합하지 않는다.
- **소유권/공개 범위 변경:** 소유권은 관리 권한을 넘기는 일이고 공개 범위는 콘텐츠 접근 대상을 바꾸는 일이다. 권한 경쟁·마지막 소유자·미디어 URL 정책까지 영향을 준다. 기존 기능은 유지하되 이번 UI 작업에서 새 정책이나 동선을 추가하지 않는다.
- **로고 업로드:** 밴드별 로고 파일을 업로드하고 헤더 등에 표시하는 기능이다. 파일 형식/크기 검증, R2 저장·교체/삭제 및 표시 정책이 추가된다. 이번에는 공통 기본 브랜드와 밴드 이름을 사용한다.
- **운영 R2 일괄 변경·재변환:** 기존 영상/음원을 대량 교체·삭제하거나 다시 인코딩하는 운영 작업이다. 원본 손실, 객체·DB 참조 불일치 및 큰 CPU 사용 위험이 있다. 개별 영상 삭제 기능의 권한 제한은 이번에 포함하지만 일괄 작업/재변환은 별도 확인 후에만 진행한다.
- **밴드별 색상 선택·저장:** owner가 palette를 선택해 구성원 전체에 적용하는 기능이다. 먼저 공통 디자인 경계를 안정화하고 preset 대비 검증과 theme_key migration을 준비해야 한다. 이번에는 토큰 기반만 만들고 실제 설정 UI/DB 저장은 후속 단계다.
- 코드·DB·배포는 계획 승인 후 진행한다. 이 문서는 현재 docs 정책에 맞춰 로컬에 저장하며 이번에 commit/push하지 않는다.

### 제외 목록 정리 메모

- 이전 답변의 4번(자유 CSS 편집)과 5번(운영 소개 일괄 삭제)은 사용자 요청으로 제외 목록에서 제거했다. 기능을 새로 추가하거나 운영 데이터를 삭제하라는 승인으로 해석하지 않는다.
- 5번은 "소개를 지우는 일반 기능"이 아니라 관리자가 DB에서 여러 밴드 소개를 한꺼번에 지우는 별도 작업을 가리켰다. 이번에는 owner가 자기 밴드 소개를 편집/비우는 기능이 이미 포함되므로 별도 제외 항목으로 강조할 필요가 없다.
