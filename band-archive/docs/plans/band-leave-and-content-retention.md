# 밴드 탈퇴와 콘텐츠 보존·삭제 권한 계획

- 작성일: 2026-10-15
- 상태: 사용자 정책 확정, 구현 전 계획. 이 문서 작성은 구현·운영 변경·push·배포 승인이 아니다.
- 적용 범위: 밴드 멤버십 탈퇴, 밴드 도메인 콘텐츠 삭제 권한, 관련 FE 동선, 업로드·미디어 삭제의 안전 경계.
- 관련 계획: [밴드 소개·공통 디자인·승인 메일 계획](band-profile-and-design-system.md)의 기존 7절 영상 전용 정책은 이 문서의 더 넓은 콘텐츠 삭제 정책으로 확장·대체한다.

## 요약 및 확정 정책

- 밴드 멤버는 탈퇴할 수 있다. 멤버십 탈퇴는 콘텐츠 삭제를 뜻하지 않는다.
- 탈퇴자가 작성한 콘텐츠도 자동 삭제하지 않는다. 탈퇴는 해당 밴드의 멤버십 상태와 탈퇴 시각만 갱신하며 콘텐츠, 작성자 관계, 저장 키, 공개 설정은 그대로 둔다.
- 댓글·답글·추천글·곡·합주를 포함한 모든 밴드 콘텐츠의 삭제는 해당 밴드의 활성 owner 또는 DB에서 확인된 활성·이메일 인증 superadmin만 가능하다.
- 사용자 확인 범위에서 “모든 콘텐츠”는 Song, Rehearsal, Media, PersonalLog, GalleryImage, Comment와 답글, SongSuggestion, Announcement, Member 프로필 등 밴드 도메인 자료를 포함한다.
- 본인 작성, admin 역할, 과거 멤버십, 요청자 본인 확인은 삭제 권한을 주지 않는다. left 멤버·비회원·정지/미확인 계정도 거부한다.
- 삭제 실패는 권한 실패, 대상 미존재/비가시성, 작업 중 충돌을 구분하되 교차 밴드 콘텐츠 존재 여부를 불필요하게 노출하지 않는다.
- 감사 이벤트는 행위자, band/content 유형과 ID, 승인 경로, 사유, 결과를 최소 기록한다. 콘텐츠 본문·인증정보·서명 URL은 기록하지 않는다.
- 플랫폼 superadmin은 콘텐츠별 삭제 작업에만 예외 권한을 가진다. 일반 읽기, 업로드, signed URL 및 밴드 권한 검사를 전역 우회하지 않는다.
- owner는 다른 활성 멤버에게 소유권을 이전하고 확인한 뒤 탈퇴한다. 본인·외부 사용자·가입 대기자는 이전 대상으로 거부한다. 혼자 남은 owner는 대상을 만들거나 밴드를 삭제하지 않고 탈퇴를 막으며 이유를 안내한다.
- UI는 기존 owner transfer 절차를 재사용하고 대상 멤버의 신원을 확인할 수 있게 표시한다. 소유권 이전과 탈퇴를 한 번의 버튼 액션으로 성공했다고 간주하지 않는다.
- 밴드 폐쇄, 계정 삭제, 법적 보존 검토는 이번 범위가 아니다. 계획·테스트 과정에서 운영 R2 파일 삭제나 대량 변환을 실행하지 않는다. 출시 후 owner/superadmin이 앱에서 권한 있는 자기 대상의 개별 삭제를 확인·요청하는 정상 동작마다 별도 채팅 승인을 요구하는 뜻은 아니다. 별도 확인은 Codex/운영자가 수행하는 실제 운영 파일 조작·일괄 작업을 가리킨다.

## 1. 의미와 불변 조건

### 멤버십 탈퇴와 재가입

- 탈퇴는 기존 `leave` POST 경로를 사용한다. 성공 시 기존 membership 행의 상태를 `left`로 바꾸고 `left_at`을 기록한다.
- membership 행과 Member 프로필 FK를 유지한다. authored content, 관계, 콘텐츠 수, object keys, visibility 및 현재 공개 URL 정책을 변경하지 않는다.
- 탈퇴는 감사 이벤트를 남길 수 있지만 메일/outbox 이벤트를 만들지 않는다.
- 반복 탈퇴는 이 밴드에 해당 사용자의 기존 `left` membership 행이 실제로 있을 때만 멱등 결과를 반환한다. 이력이 없는 사용자, 다른 사용자, 요청 `band_id`와 연관 없는 membership, 삭제된 밴드는 존재 여부를 노출하지 않는 404 정책을 따른다.
- 인증 실패와 멤버십/역할 거부는 기존 v2 인증·권한 오류 계약을 따른다. 탈퇴 API에서 다른 사용자 ID나 임의 membership ID를 받아 처리하지 않는다.
- 탈퇴 결과는 “멤버십이 left 상태”임을 나타내는 최소 DTO로 한정한다. 탈퇴자의 콘텐츠 목록·다른 밴드의 membership·초대 정보는 불필요하게 응답하지 않는다.
- 탈퇴 트랜잭션은 membership 상태와 `left_at`만 변경한다. 이미 존재하는 본인 `left` 행만 멱등 대상이다. 이력이 없는 행을 새로 만들거나, 타 사용자·타 밴드 상태를 결과로 돌려주지 않는다.
- 재가입은 현재 가입 요청 승인 또는 유효 초대 코드 흐름을 재사용한다. 기존 membership ID를 보존하고 role은 `member`로 초기화한다. 과거 owner/admin 권한을 복구하지 않는다.
- 콘텐츠 작성자 가시성 필터는 같은 밴드의 membership 존재를 기준으로 유지할 수 있다. `ACTIVE` 여부만으로 기존 작성 콘텐츠를 숨기지 않는다.
- 목록/상세 조회에서 작성자 membership을 inner join하는 경우, 탈퇴 또는 재가입 전후에 기존 작성 콘텐츠가 사라지지 않는지 확인한다.
- 재가입 뒤 작성자 표시는 기존 Member/user 관계와 표시 이름 정책을 따른다. 과거 콘텐츠의 owner/admin 작성 권한을 소급 복구하지 않는다.
- 탈퇴 동작에서는 Member 프로필을 삭제하지 않는다. 별도의 Member 콘텐츠 삭제는 일반 밴드 콘텐츠와 동일한 owner/superadmin 삭제 정책을 적용한다.

### 삭제 권한의 공통 정의

- 실제 API와 `can_delete` 표시가 같은 서버 권한 helper를 사용한다. UI flag는 편의 표시일 뿐 서버 검증을 대체하지 않는다.
- 해당 밴드의 활성 owner가 일반 밴드 콘텐츠를 삭제할 수 있다. 해당 콘텐츠의 작성자 여부는 추가 권한이 아니다.
- 활성·이메일 인증 superadmin의 예외는 명시적으로 지원하는 삭제 작업에 한정한다. 토큰의 app metadata, 하드코딩 이메일, 문자열 역할 주장만으로 superadmin을 인정하지 않는다.
- superadmin은 밴드 비회원인 경우 별도 운영 삭제 진입점만 사용한다. 삭제 사유, 이중 확인, 대상 식별, 감사 로그를 요구한다.
- 단순 band admin, 작성자 본인, 일반 멤버, 탈퇴 멤버, 미확인/정지 계정은 삭제하지 못한다.
- 기존 `can_edit`, 작성, 투표 및 열람 정책은 바꾸지 않는다. 단, soft delete, 공지 비우기/clear action, 파일 교체, 부모 삭제 cascade 등 다른 기능이 완성 콘텐츠 삭제권을 우회할 수 없게 한다. 현행 공지 PUT은 content를 요구하며 별도 DELETE는 없다. 구현 시 일반 PUT의 빈 문자열 거부를 유지한다.
- 추천곡의 “곡으로 진행”은 기존 추천 행을 삭제한다. 이 작업은 삭제 권한(owner/superadmin)과 기존 생성 권한을 모두 확인하며 `can_proceed`를 삭제 권한과 별도 표현한다. 단순 admin 권한을 추가하지 않는다.
- 모든 주요 v1 삭제/관리 경로는 동일한 권한 계약을 적용하거나 닫는다. `LEGACY_V1_WRITES_ENABLED=true`, 무인증 DELETE, 문자열 admin, 과거 비밀번호 경로는 우회 수단이 될 수 없다.

## 2. 보존·열람·URL 계약

- 탈퇴 직후 작성자의 공개 콘텐츠는 공개 방문자에게 계속 보인다. 멤버 전용 콘텐츠는 탈퇴자가 더 이상 열람하지 못한다.
- 공개/멤버 전용 갤러리, 곡·합주 미디어, 개인 기록의 URL 발급은 요청 시점의 현재 권한 및 visibility를 다시 확인한다. 탈퇴자가 예전 멤버라는 이유로 URL을 재발급하지 않는다.
- 목록 DTO가 숨긴 콘텐츠 ID를 클라이언트가 직접 요청하더라도 상세/API와 media signer가 같은 scoped authorization을 수행한다.
- signed URL은 bearer capability로 취급한다. 로그·감사 메모에 전체 URL/token을 남기지 않으며, 탈퇴 응답에 새 서명 URL을 포함하지 않는다.
- 이미 발급된 signed URL은 기존 만료 계약을 유지한다(현재 상한: 멤버 전용 5분, 공개 1시간). 탈퇴만을 위해 JWT 전체를 revoke하지 않는다. 다른 밴드 세션을 끊지 않는다.
- 캐시나 CDN에 이전 권한 응답이 남아도 API의 URL 발급과 보호 콘텐츠 접근은 서버 권한 검사를 통과해야 한다.
- 작성자 표시 정책은 기존 band-scoped 작성자 표시를 보존하되, 탈퇴를 이유로 계정 전역 개인정보를 새로 공개하지 않는다.

## 3. 탈퇴 API·경합·업로드

### API 및 소유권 이전

- 기존 POST 탈퇴 endpoint의 요청/응답 형태를 우선 유지하고, 성공 시 band ID/slug와 현재 사용자 membership 결과만 반환한다. 본인의 다른 가입 밴드 카드도 정상 탈퇴 대상이며 현재 선택 band와 일치해야 한다는 조건을 두지 않는다.
- active admin/member는 확인 후 바로 탈퇴할 수 있다. owner는 탈퇴 전에 선택한 다른 활성 멤버에게 기존 ownership-transfer API로 이전한다.
- 이전 대상은 같은 밴드에서 활성 상태인 다른 사용자여야 한다. self-transfer, 타 밴드 ID, 비회원, pending, left 대상은 실패한다. 현재 transfer API의 활성 membership 검사만으로 계정이 활성인지 보장되지 않으므로, 대상 `AppUser`의 정지/비활성 상태도 확인하도록 계약을 강화한다.
- 이전 성공과 탈퇴는 한 원자적 동작이라고 가장하지 않는다. 이전 후 탈퇴가 실패하면 새 owner 상태는 유지하고, 재시도 방법을 안내한다. 자동 ownership rollback은 하지 않는다.
- 혼자 남은 owner는 탈퇴할 수 없다. 탈퇴 차단 사유를 설명하고 임의 ownerless 상태나 밴드 삭제를 만들지 않는다.
- 멤버십 변경과 콘텐츠 삭제/업로드 권한이 서로 덮어쓰지 않도록 잠금 순서를 정하고 PostgreSQL 경합 테스트를 수행한다.

### 진행 중인 업로드

- 초기 제품 정책: 해당 밴드에 사용자의 byte 전송 또는 완료 가능한 업로드 세션이 남아 있으면 탈퇴를 409로 보류한다. 사용자는 업로드를 완료하거나 명시 취소한 뒤 재시도한다.
- 이 검사에는 다른 기기의 세션과 직접 업로드(`DirectUploadSession`), media/log 경로의 `initiated`/`completing` 상태도 포함한다. 다른 밴드의 업로드는 영향을 받지 않는다.
- FE는 client-side 업로드 작업 목록만으로 “진행 중 없음”을 결정하지 않는다. 최종 판단은 서버가 현재 band-scoped persisted session을 검사한다.
- 보류 응답에는 사용자가 어떤 상태를 완료/취소해야 하는지 식별 가능한 최소 설명을 제공하되 다른 기기·사용자 업로드의 비밀 정보를 노출하지 않는다.
- 탈퇴와 새 업로드 시작/완료는 같은 band→membership 잠금 규약을 사용한다. 업로드 completing 전환 뒤 commit 사이에 활성 membership을 다시 검사한다.
- 완료가 먼저 커밋되면 콘텐츠는 남고 탈퇴 후에도 정책에 따라 표시된다. 탈퇴가 먼저 완료되면 후속 완성 record 생성을 거부한다.
- DB record 저장 후 오디오 추출 등 후처리가 남은 것은 미완료 byte 업로드가 아니다. 탈퇴를 막지 않고 저장된 콘텐츠를 보존한다.
- 기존 임시 세션 TTL·abort 정리 계약을 재사용한다. 탈퇴를 이유로 용량을 조기 해제하거나 완료 파일을 정리하지 않는다.

## 4. 부모 삭제, 파일 저장소, 지속성 작업

- 곡·합주·멤버/개인 기록 등 부모 삭제는 자식 업로드가 남아 있으면 기본적으로 409로 막고, 먼저 자식 콘텐츠를 개별 삭제하도록 안내한다. 부모 cascade로 권한 검사를 건너뛰지 않는다.
- 삭제 권한은 soft delete, 공지 비우기, 미디어 교체/덮어쓰기, legacy API 및 관리자 도구에도 적용한다. 작성 기능이나 visibility 수정 권한은 이 정책만으로 확대하지 않는다.
- owner/superadmin 전용 공지 clear action은 내용을 비우되 band당 singleton row는 유지한다. 기존 PUT의 빈 content 허용으로 우회하지 않으며, 조회가 공지 미존재로 회귀하지 않게 한다. 이 동작도 공통 `can_delete`와 감사 로그를 사용한다.
- 현재 미디어 cleanup helper가 canonical 키를 모두 처리한다고 가정하지 않는다. 저장된 원본/오디오/파생본 키와 legacy fallback을 정규화하고, Media와 PersonalLog를 포함한 모든 참조를 점검한다.
- 여러 DB 행이 canonical key를 공유할 수 있으므로 다른 참조가 남아 있으면 object를 지우지 않는다. 삭제 대상과 실제 object key의 소유 관계를 검증하고 경로 조작/교차 밴드 키를 거부한다.
- R2와 DB는 원자적이지 않다. durable deletion task/tombstone 등 지속성 있는 재시도 수단을 설계하고, 일부 파일 삭제·DB 실패·프로세스 중단 뒤에도 멱등하게 재개한다.
- DB commit이 실패했을 때 이미 지운 object를 되돌릴 수 있다고 가장하지 않는다. 참조/작업 레코드를 기반으로 복구 또는 안전한 재시도 경로를 명시한다.
- 삭제 대기 중에는 안전한 URL 발급을 중단하거나 보수적으로 거부한다. 작업은 대상 키와 참조를 재검증하고, 성공/실패/재시도 횟수 및 사유를 안전하게 관측한다.
- 운영자용 작업 관측은 내부 task ID, 단계, 제한된 실패 범주와 시각을 제공한다. 자격 증명, signed URL, 사용자 콘텐츠 본문 및 object key 전체는 일반 응답/로그에 노출하지 않는다.
- 중복 요청은 같은 삭제 대상을 여러 번 파괴적으로 처리하지 않고 기존 작업 또는 완료 결과에 수렴해야 한다. 재시도는 현재 DB 참조를 다시 확인한다.
- 필요 migration은 별도 구현 단계에서 설계·검토한다. 운영 DB 변경은 백업·검증 및 별도 확인 조건을 통과하기 전 수행하지 않는다.
- 테스트는 모의 저장소를 사용한다. 실제 운영 R2 원본 삭제, 대량 재변환, 임의 object 탐색은 하지 않는다.

## 5. FE 동선과 클라이언트 상태

- `/bands`의 계정 화면에서 사용자가 각 내 밴드 카드의 관리가 아닌 일반 멤버 동선으로 “밴드 탈퇴”에 접근할 수 있다.
- 확인 문구에는 탈퇴 후에도 내가 작성한 콘텐츠가 남으며, 작성자 본인도 이를 삭제할 수 없다는 점을 명확하게 표시한다.
- owner는 탈퇴 확인 전 소유권 이전 단계를 거친다. 대상 목록은 서버가 반환한 활성 멤버만 제공하고, 이전 성공 후 탈퇴 실패 시 새 owner를 되돌리지 않고 재시도 안내를 표시한다.
- 409 진행 중 업로드 응답에는 완료/취소 후 다시 시도하도록 안내한다. 다른 밴드 업로드가 이유 없이 차단되지 않도록 한다.
- 성공하면 해당 밴드 데이터와 private cache, 이전 selected-band localStorage 값을 정리하고 `/bands`로 이동한다. 탈퇴 전용 상태 갱신에서는 BandContext의 `activeBands[0]` 자동 선택을 억제해 다른 밴드를 자동 선택/진입하지 않는다. 계정 전체의 기존 선택 로직은 불필요하게 전면 변경하지 않는다.
- 공개 slug 직접 방문은 기존 public viewer로 남긴다. 탈퇴 후 멤버 전용 API/이미지 링크는 서버가 거부한다.
- 같은 브라우저의 다른 탭에는 최소 storage/BroadcastChannel 무효화 신호를 보낸 뒤 focus 시 서버 권한을 재조회한다. 이 신호는 권한 증명이 아니며 실시간 모든 기기 로그아웃을 약속하지 않는다.
- 계정/밴드/세션 epoch를 이용해 오래된 응답을 차단한다. 탈퇴·이전·다른 밴드 전환 중 stale data, picker 상태, 업로드·플레이어 상태가 다른 밴드로 섞이지 않게 한다.

## 6. 순서와 단위 커밋

1. **정책 계약·권한 테스트:** 전체 콘텐츠 정의, role/user/band 매트릭스, v1/부모 cascade 경로를 목록화한다. `can_delete`와 실 API 공통 정책을 테스트로 고정한다.
2. **삭제 권한 공통화·우회 차단:** 모든 직접 삭제·soft delete·추천 진행·공지 clear·파일 교체 경로에 owner/superadmin 기준을 적용한다. 테스트 없이 API를 먼저 노출하지 않는다.
3. **탈퇴·보존 API:** 기존 leave POST를 멱등 처리하고 owner 이전 절차, membership 보존, 업로드 경합 및 작성자 조회 회귀를 구현한다.
4. **FE 탈퇴 동선:** 내 밴드 카드, 콘텐츠 잔존 확인, owner transfer, 409 안내, cache/localStorage 정리와 stale response 차단을 연결한다.
5. **지속성 미디어 삭제:** 현재 v2 gallery/media/personal-log/member DELETE 경로가 없음을 전제로 scoped endpoint를 설계한다. canonical/legacy 키와 공유 참조 검증, durable task/retry 및 URL 발급 경계를 구현한다. 필요 스키마/운영 DB 변경은 별도 승인 전 수행하지 않는다.
6. **미디어 삭제 UI/API:** 갤러리·곡·합주·개인 기록 등 scoped delete와 비회원 superadmin 전용 별도 운영 진입점을 제공한다. 사유/이중 확인/감사 기록을 포함한다.
7. **전체 검증:** 전체 BE/FE 테스트와 DB 동시성 테스트를 수행하고 권한표·공개 URL·부분 실패·재시도를 검토한다. 변경 범위에 필요한 단위 커밋을 만든다.
8. **출시:** 서버 측 삭제 경계가 모든 경로에서 강제되고 탈퇴 UI/API가 함께 검증된 뒤 순차 출시한다. 프로젝트의 상시 승인 범위에 맞춰 필요한 BE/FE 배포와 일반 push를 진행하되, DB migration, R2 실제 삭제, 비밀/비용 설정 변경은 별도 확인 조건을 유지한다.

## 7. 필수 검증 매트릭스

- 사용자 2명·밴드 2개 이상: owner, admin, member, left, pending, 비회원 superadmin, 비활성/미인증 superadmin, 정지 사용자.
- 모든 삭제 API에 동일 사용자/콘텐츠를 적용해 owner와 활성 인증 superadmin만 성공하고 나머지는 같은 보안 결과를 받는지 비교한다.
- 권한 확인 직후 membership이 left 되거나 owner가 바뀌는 경합에서 commit 시점 권한으로 재검증되는지 확인한다.
- role flag와 실 API 권한의 parity를 확인한다. 화면에서 버튼을 숨겨도 직접 URL/API 호출은 서버에서 거부되어야 한다.
- 교차 밴드 ID, 잘못된 콘텐츠 ID, 다른 유형의 object key, 공유 object를 넣어 404/거부 동작과 데이터 불변을 검증한다.
- 탈퇴 반복 호출, 타 밴드 ID, 계정 전환, left 후 재가입 승인/초대, membership ID 유지, role member reset, 과거 권한 미복원.
- 탈퇴 전후 모든 콘텐츠 DB count/hash와 relation/object key/visibility 불변, R2 삭제 호출 0회, outbox/mail 이벤트 0건.
- 탈퇴에서 audit 이외의 outbox/메일/푸시/콘텐츠 cleanup side effect가 없음을 확인한다.
- owner 본인 이전 거부, 활성 다른 멤버 이전 성공, pending/left/외부 대상 거부, 마지막 owner 차단, 이전 성공 후 탈퇴 실패 시 ownership 보존.
- owner/superadmin delete 허용; admin/member/uploader/left/anonymous/invalid superadmin 거부. 밴드 비회원 superadmin은 별도 승인 운영 경로만 허용.
- 비회원 superadmin 경로는 밴드 콘텐츠 임의 열람 권한을 주지 않고, 삭제 사유와 대상 ID의 감사 기록만 남기는지 확인한다.
- 각 콘텐츠 종류, 댓글 답글, 추천 “곡으로 진행”, 공지 clear, soft delete, 파일 교체, v1 proxy, `LEGACY_V1_WRITES_ENABLED` 포함. 설정 기본값이 true여도 운영 값을 확인된 것으로 가정하지 않는다. true일 때 기존 legacy handler가 인증을 요구하지 않는 경로는 공통 정책을 강제하거나 폐쇄한다.
- 일반 공지 PUT의 빈 content는 계속 거부하고 clear action은 row를 삭제하지 않는지 확인한다.
- 업로드 initiated/전송/completing·탈퇴 경합, 같은 밴드 잠금, 다른 밴드 업로드 무영향, 업로드 완료 우선/탈퇴 우선 각각 검증.
- owner transfer와 delete/leave를 함께 실행해 락 순서가 교착을 만들지 않고 최종 owner만 허용되는지 확인한다.
- public vs MEMBERS 접근, 재발급 URL 권한, signed URL 기존 TTL, 탈퇴자가 멤버 전용 URL 재발급 불가.
- 공유 canonical object key, legacy key fallback, 다른 테이블 참조, 부분 R2 실패/DB rollback/작업 재시작/반복 재시도 및 삭제 완료 후 URL 거부.
- task 처리 중 동일 대상 재요청, worker 재기동, DB 연결 끊김, 저장소 timeout을 재현하고 중복/누락 삭제가 없는지 확인한다.
- 동일 브라우저 다른 탭 무효화, 다른 밴드 자동 진입 없음, 공개 slug viewer 유지, stale account/band 응답 차단.
- 테스트 전부 격리된 fixtures와 mock object storage를 사용하며 사용자/운영 데이터나 파일을 지우지 않는다.

## 8. 제외 범위 및 승인 경계

- 밴드 폐쇄·삭제, 계정 삭제, 법적 보존·요청 검토는 별도 정책/계획 없이는 구현하지 않는다.
- pending 가입 요청 취소, 밴드 탈퇴 후 다른 밴드 처리, 계정 전체 로그아웃은 추가하지 않는다.
- 탈퇴 시 콘텐츠 익명화/작성자 변경, 자동 삭제, 공개 범위 변경은 하지 않는다.
- 운영 DB에서의 schema migration/수동 데이터 조작, Codex/운영자가 수행하는 운영 R2 원본 파일 삭제·대량 변환, secret/비용 설정 변경은 별도 확인이 필요하다. 정상 배포된 앱을 통해 owner/superadmin이 허가된 단일 콘텐츠 삭제를 요청하는 일상 동작마다 별도 승인을 요구하지 않는다.
- 이 문서와 crosslink의 계획 커밋은 허용된다. 계획 저장/커밋만으로 기능 소스 구현, 기능 소스 커밋, push, 배포 또는 운영 데이터 변경을 시작하지 않는다.
