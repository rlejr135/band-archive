# 밴드 가입자 자동 멤버 프로필 계획

작성일: 2026-10-17. 사용자가 계획의 구현을 승인했다. 운영 DB 변경·누락 프로필 생성은 별도 확인 중이며, 승인 전에는 로컬 구현과 테스트만 수행한다. 구현은 BE·FE·운영 검토 서브에이전트로 나누고 총괄이 검토·단위 커밋한다.

## 구현 계약

- 본인 API는 GET/PATCH `/api/v2/bands/{bandId}/members/me`이며 응답은 기존 상세와 같은 `member` envelope를 기준으로 FE·BE가 함께 확정한다.
- `biography` 최대 300자, `positions`는 VOCAL/GUITAR/BASS/DRUMS/KEYBOARD/OTHER 중 복수 선택, `custom_position`은 OTHER를 선택했을 때만 최대 50자다.
- `profile_revision`을 PATCH에 제출하여 오래된 화면의 덮어쓰기를 409로 차단한다. 이번 단계에서는 이름 수정은 제공하지 않는다.
- 운영 DB 변경과 배포는 테스트·기존 데이터 대조·백업 복원 검증 후 진행한다. R2 작업·재변환·메일 설정 변경은 없다.

## 진행 기록

- FE 구현과 전체 266개 테스트·집중 37개 테스트·변경 파일 lint·빌드 검증을 완료했다. 본인 표시, 소개·복수 포지션 편집, 충돌 시 명시적 재조회, 기존 악기 표기 보존, 탈퇴자 기록 읽기를 포함한다. FE 커밋은 `300dc27`이며 아직 운영에 push하지 않았다.
- 운영 v17 스키마를 TLS 검증된 읽기 전용 연결로 확인했다. 전체 활성 계정은 2개지만 들뜬의 활성 가입자는 Gmail owner 1명이며, 다른 계정의 가입 요청은 거절 상태다.
- 사용자는 기존 `ser` 프로필이 본인 것임을 확인하고 band 1 / member 1 / user 1의 명시적 연결과 베이스 설정을 승인했다. 작은 DB 백업과 데이터 대조를 수행하되 이번 운영 데이터 복원 리허설은 생략하도록 승인했다. 다른 계정·기존 기록·R2 객체는 보존한다.
- 최종 전체 BE 테스트는 **922 passed**(실패 0, 기존 경고 918, 675.75초), FE 전체는 **266 passed**, 운영 FE 빌드는 성공했다. 별도 로컬 PostgreSQL 운영 도구 검증 5개와 backfill·보존 계약 검증 20개도 통과했다. 운영 DB를 사용하는 테스트나 실제 미디어 재변환은 하지 않았다.
- 전체 BE 로그 SHA-256: `1ad4b87e1a66328357cfeb0a908367af2c03105792367e479c2ec1f72add5606`. 배포 대상 기능 소스는 `aab0bee`이며 운영 적용 결과는 아래 기록을 추가한다.
- 2026-10-18 KST: 운영 public 스키마의 작은 일관성 백업(173,353 bytes)을 저장하고 해시·34개 테이블·기존 권한·명시적 연결 manifest를 검증했다. 사용자 승인대로 복원 리허설은 생략했다. 백업 dump SHA-256은 `61c54f23652d8e75f508fb69b91c3744b477bb6b94817a39e204e51aab89f20f`이며 비공개 로컬 `.state`에 보관한다.
- 운영 `20261017_17 → 20261017_18`과 member 1 / user 1 연결을 단일 트랜잭션으로 적용했다. 신규 프로필 0개, 승인된 기존 프로필 연결 1개이며 기존 행·catalog·ACL/RLS 보존과 새 연결의 startup 검증이 통과했다. 적용 보고서 SHA-256: `7c1da3925486bb392c1dad5f0c5a9f4666014a59797d352fbb169323cfe8b84a`.
- 별도 정확한 대상 검증 후 member 1의 포지션을 `BASS`/`베이스`로 설정했다. 이름·소개·기존 연습 기록을 보존하고 revision은 1이다. 새 읽기 전용 연결의 검증이 통과했다. 보고서 SHA-256: `9be09c2aca6f9a60670182e1dfded2d756c1a5123d6a934b4be2b4bf360a119b`.

## 목표

- 활성 밴드 가입자는 역할에 관계없이 멤버 탭에 본인의 프로필이 정확히 하나 존재한다. member/admin/owner 모두 동일하다.
- superadmin도 해당 밴드의 활성 멤버라면 동일하게 적용한다. 플랫폼 권한만 있고 가입하지 않은 superadmin을 모든 밴드에 자동 추가하지는 않는다.
- 각자 밴드별로 자기소개와 담당 포지션을 설정한다. 계정의 전역 프로필이나 다른 밴드의 프로필은 변경하지 않는다.

## 현재 구조와 변경 방향

- BandMembership은 계정의 밴드 가입 상태·역할, Member는 멤버 탭과 개인 연습 기록의 대상이다. Member에는 band_id, 선택적 linked_user_id, name, instrument가 있다.
- 가입 승인·초대 가입·밴드 생성 승인에서 활성 멤버십을 만들지만 Member 생성은 연결되어 있지 않다. 현재 멤버 상세 화면도 읽기 중심이다.
- 기존 Member와 PersonalLog 연결을 유지하고 자동 프로필 보장 서비스를 공통화한다. 기존 Member ID나 연습 기록의 소유 관계를 이름만 보고 바꾸지 않는다.

## 사용자 흐름

1. 가입 요청 승인, 초대 코드 가입, 밴드 생성 승인으로 owner가 되는 경우 모두 활성화와 프로필 보장을 한 트랜잭션에서 처리한다. pending/rejected에는 공개 프로필을 만들지 않는다.
2. 멤버 탭에서 본인 카드에 '나' 표시와 '내 프로필 수정'을 제공한다. 상세 화면에서도 수정 가능하다.
3. 프로필 자동 생성은 필수지만 자기소개·포지션 입력을 강제하거나 다른 기능을 막지는 않는다. 미입력은 '소개를 작성해 주세요', '포지션 미설정'으로 표시한다.
4. 자기소개는 최대 300자 평문, 포지션은 보컬·기타·베이스·드럼·키보드·기타 악기/역할 중 복수 선택을 제안한다. 기타 역할에는 제한된 길이의 직접 입력을 허용한다. 보컬+기타 같은 겸임을 지원한다.
5. 가입 심사 때 쓴 join_introduction은 심사용이다. 현재 승인 때 제거하는 정책을 유지하며 새 자기소개에 자동 복사하거나 공개하지 않는다.
6. 표시 이름은 계정 표시 이름을 초기값으로 사용하고 이메일을 대신 노출하지 않는다. 이름이 없으면 중립적인 기본 이름을 사용한다. 밴드별 이름 편집 제공 여부는 구현 시 기존 이름 정책과 함께 확정한다.

## 프로필·가입 상태의 일관성

- 같은 band_id + linked_user_id에 연결 프로필 한 개만 허용한다. 연결되지 않은 레거시 프로필은 여러 개 보존할 수 있다.
- 가입·승인 재시도 및 동시 요청에도 중복 생성하지 않는다. 공통 helper와 DB 유일 제약으로 보장한다.
- 역할 변경·owner 이전은 프로필을 새로 만들거나 지우지 않는다. 소유권 수령 등 활성화 경로도 빠짐없이 점검한다.
- 탈퇴하면 활성 멤버 목록에서는 제외하되 프로필·연습 기록·기존 콘텐츠를 삭제하지 않는다. 보존 기록의 작성자나 프로필을 현재 멤버인 것처럼 표시하지 않는다. 명단 공개 설정을 우회하는 새 과거 멤버 검색 경로도 만들지 않는다.
- 기존 멤버 상세·개인 기록 링크는 원래의 명단 열람 권한 아래 읽기를 유지하고 '탈퇴한 멤버' 등 가입 상태를 정확히 표시한다. 활성 목록에서 숨기는 처리를 상세·기록까지 일괄 404로 만드는 방식으로 구현하지 않는다.
- 재가입 시 기존 연결 프로필을 재사용하고 소개·포지션·연습 기록을 보존한다.
- 활성 가입자의 연결 프로필 자체를 삭제해 필수 명단에서 사라지게 할 수는 없다. owner/superadmin의 콘텐츠 삭제 권한과 구분해 삭제 API 및 can_delete를 함께 정리한다. 개별 연습 기록 등 콘텐츠 삭제 정책은 기존대로 유지한다.
- 본인 프로필 수정은 활성 가입자 본인만 허용하고 user_id/member_id 조작으로 타인이나 다른 밴드 프로필을 바꿀 수 없게 한다. 관리자의 타인 소개 수정 기능은 이번 범위에 추가하지 않는다.

## 기존 데이터 처리

1. 기존 활성 멤버십과 연결 Member를 대조하는 읽기 전용 점검 도구를 만든다.
2. 이미 연결된 프로필은 그대로 사용한다. 연결되지 않은 옛 멤버와 계정은 이름·이메일 유사성만으로 자동 연결하지 않는다.
3. 기존 프로필 중복 후보를 보고하고 필요한 경우 관리자가 명시적으로 계정과 연결한다. 개인 기록이 딸린 프로필을 자동 병합·삭제하지 않는다.
4. 활성 가입자 중 연결 프로필이 없는 계정에만 프로필을 생성한다. 기존 들뜬 owner/admin도 포함한다.
5. 중복 연결이 있으면 유일 제약 적용을 중단하고 먼저 해소한다. expand → 점검/명시적 연결 → backfill → 검증 → 제약 적용 순서로 진행한다.
6. 운영 반영 전 별도 DB 변경 승인을 받고 백업·복원 리허설을 수행한다. R2 파일은 변경하지 않는다.

## API·스키마·프런트엔드

- Member에 자기소개·구조화된 복수 포지션을 추가한다. instrument 문자열과 기존 응답은 호환성을 위해 유지하고 포지션 표시 문자열은 공통 변환기로 처리한다. 레거시 악기 이름을 임의로 새 enum으로 바꾸지 않는다.
- band-scoped GET/PATCH `/api/v2/bands/{bandId}/members/me`를 제안한다. GET에서 생성하지 않고 쓰기·이전 단계에서 프로필을 보장한다. 부분 수정·허용 필드·길이·포지션 중복 및 오래된 수정 충돌을 검증한다.
- 기존 멤버 목록·상세 응답에 biography, positions, is_self, can_edit_profile, 가입 표시 상태를 필요한 범위만 추가한다. 이메일·내부 계정 식별자를 공개하지 않는다.
- 멤버 명단 공개 여부와 기존 열람 권한을 그대로 따른다. 공개 명단이면 소개·포지션도 외부에 보일 수 있음을 수정 폼에 안내한다. 공개 설정과 자기소개 노출 범위를 임의로 확장하지 않는다.
- 멤버 목록에는 포지션 태그·짧은 소개를 표시하고 상세에는 전체 소개와 본인 수정 폼을 둔다. 공통 버튼·테마·접근성 스타일을 사용한다.
- 목록과 상세 캐시를 저장 후 갱신한다. 계정·밴드 전환 시 요청 취소 및 폼 상태 격리를 유지한다.

## 구현 순서와 커밋

1. 계약·모델 확장 및 기존 연결/중복 점검 도구.
2. 공통 프로필 보장 서비스와 모든 가입 활성화 경로 연결, 동시성 테스트.
3. 본인 프로필 조회·수정 및 읽기 응답/삭제 일관성 정리, 권한 테스트.
4. 멤버 목록·상세·본인 소개/포지션 편집 UI와 회귀 테스트.
5. 승인 후 기존 활성 가입자 backfill·제약 확정. 전체 BE/FE 테스트·빌드, BE → FE 배포와 운영 검증.

구현은 서브에이전트, 총괄은 검토·검증·단위 커밋·배포를 담당한다.

## 완료 기준

- owner/admin/member의 신규 가입·초대 가입·밴드 생성 승인마다 활성 명단에 정확히 한 개의 본인 프로필이 있다.
- 기존 활성 가입자 누락이 없고 동시 승인·재가입·역할 변경에 중복이 없다.
- 본인 소개·복수 포지션만 안전하게 수정하고 다른 밴드·타인 수정은 차단한다.
- pending/left 계정은 활성 명단에서 제외되고 탈퇴·재가입에도 기존 콘텐츠와 개인 기록이 보존된다.
- 기존 미연결 멤버·기록을 손상하지 않고 심사용 소개·이메일이 공개되지 않는다.
- 프로필 삭제로 활성 명단 의무를 우회할 수 없으며 공개 명단 설정을 일관되게 지킨다.
