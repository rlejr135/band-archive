# 밴드 소개·로고·초대 링크·가입 요청 개편 계획

상태: 공통 소개 기반과 공개 검색 버튼 보완은 운영 배포 완료. 로고 기능도 BE 933개·FE 294개 검증 및 별도 승인 후 백업·복구 검증, 운영 DB rev19, Fly v61, Cloudflare Pages 반영·운영 검증까지 완료(2026-10-19, 기능 소스 1b2b7b0). 상세 내용은 `band-logo-local-validation.md`에 기록했다. 다음은 24시간 재사용 초대 링크 단계이며, 초대 링크의 운영 DB 변경은 아직 승인되지 않았다.

## 목표와 순서

사용자가 지정한 구현 순서를 유지한다.

1. 일반 가입 요청과 초대 링크가 함께 사용하는 밴드 소개 페이지 기반.
2. 요구사항 1: 공개 밴드 찾기의 내 밴드 링크 등 디자인 보완.
3. 요구사항 5: 관리 화면의 밴드별 상단 로고 설정.
4. 요구사항 4: 기존 초대 코드 종료 및 24시간 초대 링크 도입.
5. 요구사항 2·3: 검색에서 소개 페이지로 연결하고 일반 가입 요청 UI·오류 수정.

오류 원인에 대한 읽기 전용 사전 진단은 먼저 한다. 공통 인증·멤버십 결함이 새 초대 링크를 막는다면 그 부분만 초대 단계의 필수 수정에 포함하고 보고한다. 일반 가입 요청 화면의 개편은 마지막에 한다.

## 현재 코드에서 확인한 사항

- `DiscoverBandsContent`의 `← 내 밴드` Link에는 공통 반환 링크 클래스가 없다. 전역 button 스타일로는 anchor를 해결하지 못하므로 해당 링크를 명시적으로 수정하고 DOM 회귀 테스트를 추가한다.
- 가입 요청은 검색 화면의 requestBand 상태로 폼을 삽입한다. 요청 실패는 상세 원인에 관계없이 genericFailure로 표시한다. 실제 운영 실패 원인은 아직 확정하지 않았다.
- 초대 코드 가입 역시 FE가 인증·서버 오류까지 모두 코드 사용 불가로 표시한다. 기존 코드를 고치는 대신 새 초대 기능에서 실패 분류와 공통 기반을 바로잡는다.
- 기존 BandInviteCode는 해시 저장·폐기·발급자 기록은 있지만 expires_at이 없다. 코드 전달 방식을 URL로 바꾸는 것만으로 24시간 만료를 충족할 수 없다.
- SignupPage는 returnTo를 읽지만 emailRedirectTo는 /verify-email로 고정하고, VerifyEmailPage는 /bands 링크를 제공한다. 이메일 인증 후 초대 페이지 복귀와 만료 재검증이 필요하다.
- 현재 Band 모델에는 별도 로고 참조가 없고, 상단에는 고정 로고를 사용한다. 대표 사진은 갤러리의 is_featured로 관리한다.

## 0. 사전 계약·오류 진단

- 운영 POST를 재현해 실제 가입자를 만들지 않는다. 승인된 테스트 계정/로컬 복제 환경, 기존 로그의 비밀 없는 오류 코드, HTTP 상태, FE 요청·응답 계약을 대조한다.
- JWT 갱신, 이메일 인증, 정책 확인 gate, 밴드 가입 상태, introduction 검증, 응답 해석, DB 트랜잭션을 구분한다. 추정 원인을 확정 사실처럼 취급하지 않는다.
- API 오류를 인증 필요 / 권한 없음 / 입력 오류 / 밴드 없음 / 만료·폐기 / 일시적 서버 오류로 구분한다. 임의 토큰의 존재 여부를 알려 주는 오류 차이는 만들지 않는다.
- 소개 데이터의 공개 범위, 초대 재사용 정책, 관리자 권한을 계약 테스트로 먼저 고정한다.

## 1. 공통 밴드 소개 기반

### 화면과 경로

- `/bands/:bandSlug/about`를 가입 전에도 접근 가능한 독립 경로로 만든다. 기존 RequireAuth 내부의 작업 공간 경로와 분리한다.
- 공통 BandIntroduction 컴포넌트는 대표 사진, 밴드 이름, 곡 수, 공지, 소개만 표시한다. 전체 곡은 우선 전체 곡 목록이 아닌 요약 숫자로 해석한다.
- 검색창·검색 결과·작업용 상단 탭은 이 페이지에 두지 않는다. 돌아가기와 계정 상태를 안내한다.
- 데이터 표시 부분과 하단의 가입 행동 영역을 분리한다. 이후 일반 가입 요청 / 초대 가입 확인이 같은 소개 컴포넌트를 사용한다.
- 이미 가입한 경우 밴드 공간으로 이동, 승인 대기는 대기 상태를 표시한다. 방문만으로 가입·승인 요청을 실행하지 않는다.

### 데이터와 접근

- 기존 대시보드의 band-scope/visibility 조회·직렬화 helper를 재사용하되, 달력·멤버 명단·업로드·전체 미디어를 불러오지 않는 가벼운 소개 응답을 제공한다.
- API 초안: `GET /api/v2/bands/by-slug/{slug}/introduction`. 응답은 band identity, description, 허용된 대표 사진, 곡 수 요약, 공개 가능한 공지로 제한한다.
- 멤버 전용 사진·공지·곡 정보는 가입 전에 노출하지 않는다. 곡 수는 조회 대상에 따라 공개 곡 수임을 명시한다. 사진·공지가 비공개면 기본 이미지·안내를 사용한다.
- 비공개 밴드는 일반 공개 경로로 존재를 노출하지 않는다. 유효한 초대 링크는 해당 밴드의 제한된 소개만 보여 주고 멤버 콘텐츠 열람 권한을 주지 않는다.
- 비공개 밴드의 초대 미리보기에서 보여 줄 필드도 이 소개 계약으로 명시하며, 기존 멤버용 대시보드를 그대로 우회 호출하지 않는다.
- 공지/대표 사진/통계의 공개 범위 조합, 다른 밴드 ID 혼합, 삭제된 밴드를 테스트한다.

## 2. 공개 밴드 찾기 버튼 보완 — 요구사항 1

- 내 밴드 반환 링크에 기존 bands-return-link 등 의미에 맞는 공통 클래스를 명시한다.
- 검색·페이지 이동·작업 공간 이동 등 같은 화면의 링크/버튼과 disabled/focus/모바일 정렬을 점검한다.
- 신규 가입 화면 연결은 마지막 단계까지 기존 동작을 유지한다. 이 단계는 디자인 변경만 한다.

## 3. 관리 화면의 밴드 로고 — 요구사항 5

- 대표 사진과 별도로 BandLogo 연결 테이블에 band_id와 gallery_image_id를 저장한다. 밴드당 한 행만 허용하고, 복합 외래 키와 서비스 검증 모두 같은 밴드의 이미지인지 확인한다. Band→Gallery 순환 참조를 피하고, 사진 삭제 시 연결 행만 제거되도록 한다.
- 현재 대표 사진처럼 밴드 갤러리에서 선택·변경·해제하는 방식으로 시작한다. 새 파일 전용 업로드·크롭 도구는 이번 범위에 추가하지 않는다.
- 관리 화면에는 현재 로고와 미리보기를 표시한다. 대표 사진 선택 UI의 조회/페이지네이션/서명 URL 갱신 기반을 공유하고 두 선택 상태는 분리한다.
- 변경 권한은 앞서 정리한 owner·superadmin 계약으로 서버에서 검증한다. FE가 임의로 권한을 추정하지 않으며 superadmin 권한을 다른 관리 기능까지 확장하지 않는다.
- 상단 `<밴드 이름> Archive` 옆에 적용한다. 로고 없음·권한 없음·사진 삭제·URL 만료·이미지 오류는 중립적인 공통 기본 이미지로 대체한다. 다른 밴드의 고정 로고를 기본 이미지로 쓰지 않는다.
- R2 객체를 복사하거나 기존 사진을 삭제하지 않는다. 원본 참조와 로고 해제 정책으로 처리한다. 갤러리 삭제 후 잘못된 참조가 남지 않도록 테스트한다.
- 밴드 전환·계정 전환 시 이전 밴드의 이미지/캐시가 섞이지 않게 한다.

## 4. 24시간 초대 링크 — 요구사항 4

### 관리자 흐름

- 기존 can_manage_invites 권한(owner/admin)을 기준으로 생성·목록·폐기를 제공한다. 플랫폼 권한만으로 모든 밴드 초대 관리 권한을 자동 부여하지 않는다.
- 새 링크마다 서버 UTC 발급 시각 + 24시간으로 만료를 고정한다. FE에는 KST 만료 날짜·시간을 표시한다.
- 256비트 이상 난수 토큰을 사용하고 DB에는 해시만 저장한다. 발급 직후에만 원문 링크를 표시·복사한다. 나중에는 만료·폐기 상태만 조회하고 필요하면 새 링크를 발급한다.
- 사용자 확정: 24시간 안에 여러 사람이 사용할 수 있는 재사용 링크이며 관리자는 즉시 폐기할 수 있다. 일회용으로 소진하지 않는다.
- 별도 BandInviteLink 테이블을 추가하고, 기존 BandInviteCode 테이블은 즉시 삭제하지 않는다. 새 기능 활성화 시 기존 코드 발급·가입 API를 차단하고 UI를 제거한다. 예전 코드는 새 링크로 변환해 만료를 연장하지 않는다.
- 초대 생성·폐기·실제 가입을 감사 로그에 기록하되 원문 토큰/전체 초대 URL은 기록하지 않는다.

### 초대받은 사람의 흐름

1. 초대 링크 → 유효성 검사 → 공통 밴드 소개 + ‘OO 밴드에 가입하시겠습니까?’.
2. 비로그인이라면 로그인/회원가입으로 이동하고, 이메일 확인·필요한 정책 확인 후 같은 초대 소개 페이지로 복귀한다.
3. 로그인한 이메일 인증 계정이 명시적으로 가입 버튼을 눌러야 활성 member로 가입한다. 조회·메일 미리보기·보안 스캐너의 링크 방문으로는 가입하지 않는다.
4. 별도 관리자 승인과 자기소개 제출 없이 가입하며, 공통 멤버 프로필 보장 서비스를 호출해 멤버 탭에도 정확히 한 번 추가한다.
5. 성공 후 초대 컨텍스트를 지우고 해당 밴드로 이동한다. 기존 밴드 가입은 유지한다.

### 복귀와 보안

- 링크 토큰을 URL 경로·query에 그대로 넣어 API/프록시 로그나 Referer로 전파하지 않는다. 초안은 `/invite#token=...`이며 FE가 읽은 후 history.replaceState로 제거하고 POST body로만 전달한다.
- fragment는 로그인/이메일 인증 과정에서 자동 보존되지 않는다. 짧은 수명의 서버 초대 복귀 컨텍스트를 설계하고, 인증한 대상 계정과 바인딩한다. 이메일 콜백에는 가입 권한 토큰 대신 복귀 식별자만 전달하며, 그것만으로 가입할 수 없게 한다.
- 동일 브라우저의 단기 복귀 상태는 만료 시 정리하며 access token·비밀번호·초대 원문을 localStorage나 분석 도구에 남기지 않는다. 다른 브라우저/기기에서 확인 메일을 여는 경우도 테스트하고 복원 불가 시 원래 초대 링크를 다시 여는 안전한 안내를 제공한다.
- safeReturnPath는 승인된 같은 origin의 복귀 경로만 허용한다. 기존 /verify-email 경로와 Supabase 리디렉션 허용 설정의 호환성을 검증한다. 설정 변경이 필요하면 별도 확인한다.
- 발급·미리보기·가입 시도에 rate limit과 no-store를 적용하고 초대 페이지의 Referrer-Policy 및 제3자 요청을 제한한다.
- 가입 시 서버에서 만료·폐기·밴드 삭제·계정 상태를 다시 검증한다. 미리보기 이후 만료된 경우 가입을 거절한다.
- 만료·폐기·무효 링크는 ‘사용할 수 없는 초대 링크입니다. 관리자에게 새 링크를 요청해 주세요’로 통합한다. 네트워크·서버 장애와는 구별한다.
- 이미 활성 가입자는 중복 생성하지 않고 밴드 열기를 제공한다. pending은 초대 승인으로 활성화, left/rejected는 기존 정책에 따라 일반 member로 재가입하고 옛 관리자 권한은 복구하지 않는다.
- 폐기/가입 경쟁·중복 클릭·응답 유실 후 재시도는 같은 잠금 순서와 유일 제약으로 처리한다. 원문 토큰을 지웠거나 결과가 불명확하면 자동 가입 재시도하지 않는다.

## 5. 소개 페이지 기반 일반 가입 요청 — 요구사항 2·3

- 공개 검색의 가입 요청은 `/bands/:bandSlug/about`로 이동한다. 검색 화면 안의 requestBand 폼과 중복된 가입 상태 로직을 제거한다.
- 소개 아래 선택 자기소개(기존 300자 제한 유지), 요청 보내기, 취소/돌아가기를 배치한다. 승인 심사용 소개를 공개 프로필 소개에 복사하지 않는다.
- 로그인 복귀 시 대상 밴드를 유지한다. 요청 중 중복 클릭 방지, 실패 시 입력 보존, 오류 영역 포커스/라이브 안내를 제공한다.
- 성공은 ‘가입 요청을 보냈습니다. 관리자 승인 대기 중입니다’로 명시한다. 가입 완료, 대기 중, 재가입 요청, 밴드 없음, 인증 만료, 입력 오류, 서버 장애를 구분한다.
- 사전 진단으로 확보한 재현 테스트를 먼저 추가하고 실제 결함을 수정한다. 오류 문구만 바꾸고 실패 원인을 덮지 않는다. 서버 성공 후 목록 갱신 실패를 가입 요청 실패로 오인하지 않는다.
- 검색/소개/내 계정/빠른 밴드 전환기의 멤버십 정보를 재사용·갱신하고 계정/밴드 전환의 지연 응답이 섞이지 않게 한다.

## 단위 커밋·검증·배포

1. 소개 조회 계약/테스트 → BE 최소 조회 및 FE 공통 소개 shell.
2. 공개 검색 버튼 보완.
3. 로고 schema migration → 권한·선택 API/테스트 → 관리·상단 UI/회귀 테스트.
4. 초대 링크 schema/계약 → 발급·미리보기·가입 서비스/동시성 테스트 → 인증 복귀·관리·확인 UI → 코드 경로 종료.
5. 일반 가입 오류 재현·수정 → 검색에서 소개 페이지 연결·가입 상태 UI → 전체 회귀 검증.

구현은 FE/BE 담당 서브에이전트가 수행하고, 총괄은 계약 확인·리뷰·검증·단위 커밋·배포를 맡는다. 서로 다른 폴더의 동시 수정은 파일 소유 범위를 분리한다.

- 공통 인증/가입 서비스 관련 BE 전체 pytest, FE 전체 테스트와 변경 파일 lint·운영 빌드를 실행한다.
- 두 밴드·두 계정, 방문자·멤버·admin·owner·superadmin, 공개/비공개, 만료 시각 경계, 초대 폐기 경쟁, 재가입·이미 가입, 프로필 중복을 검증한다.
- 회원가입→이메일 확인→정책 gate→초대 소개 복귀→명시적 확인→즉시 가입을 실제 브라우저로 검증한다. 운영 가입 테스트는 테스트 계정/밴드와 필요한 쓰기 범위를 먼저 합의한다.
- PC/320px 모바일에서 소개·가입 폼·정책 링크·관리 링크·로고 fallback을 확인한다.
- 운영 DB 변경은 schema/제약/보존 범위를 설명하고 별도 승인을 받은 후 적용한다. 이전 작업의 복원 리허설 생략 승인은 이번 migration으로 확대 해석하지 않는다.
- 2026-10-18 사용자 확인: 로고·24시간 초대 링크·가입 복귀 기록 및 관련 제약은 로컬 구현과 테스트를 먼저 진행하고, 실제 변경 목록·검증 결과·백업/보존 절차를 상세 보고한 뒤 운영 DB 적용 승인을 다시 요청한다. 이번 답변 자체는 운영 DB 변경 승인이 아니다.
- 배포 가능한 기능 단위마다 BE → FE 순으로 반영하고 실제 HTTP/CORS/라이브 번들을 확인한다. 초기 소개만 배포된 시점에는 미완성 초대/가입 버튼을 노출하지 않는다.
- R2 삭제·기존 이미지 복사·영상 변환·추가 유료 서비스·실제 초대 메일 발송 자동화는 포함하지 않는다. 링크 복사와 사용자의 직접 전달을 기본으로 한다.

## 구현 전 확인할 선택

1. 확정: 24시간 동안 여러 사람 사용 + 관리자 즉시 폐기. 만료를 자동 연장하지 않는다.
